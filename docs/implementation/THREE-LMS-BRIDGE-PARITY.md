Status: active implementation and contract research, 6 September 2026 UTC.

## Scope and acceptance

- Require current human approval or valid user-selected Edit permission, one send, a fresh result check, and an explicit uncertain state. A missing response must never trigger an automatic repeat write. One explicit dispatch is not exactly-once delivery. Chrome can resend a POST by itself when a reused connection fails before the response headers arrive, so one reviewed change can reach the provider twice while Morrow sends it once. [BROWSER-POST-TRANSPORT-LIMIT.md](BROWSER-POST-TRANSPORT-LIMIT.md) holds that measurement, and every write guarantee stated in this file is bounded by it.
- Preserve each course's existing design and standards by default. Read the target and relevant course examples. Make surgical edits when appropriate. Keep unrelated HTML, media, links, settings, and assessment intent intact. Redesign only when requested. Apply these rules separately to each course in a batch. Use relevant principles from the SSH-only [ExamplePlatform knowledge review](../research/MERIDIAN-KNOWLEDGE-FOR-MORROW-2026-09-06.md).

## Shared bridge checkpoint

Canvas and Moodle now use the same extension pairing, authenticated local connection, approval flow, and single-use effect receipt. Moodle binds the exact HTTPS site, including its installation subpath, signed-in account, and open course. The previous direct-token Moodle and Blackboard implementation and startup route were removed. Blackboard has no executable browser fallback. It reaches Learn through the official Anthology REST API instead, as an internal Gateway child that no browser takes part in; [BLACKBOARD-REST-SCOPE.md](BLACKBOARD-REST-SCOPE.md) is that route's inventory, held-operation list, and acceptance runbook.

Why Blackboard has no browser path. The extension carried an unwired 3LO PKCE module, `connector/extension/src/blackboard-session.js`, with its token exchange disabled by the constant `PUBLIC_PKCE_TOKEN_EXCHANGE_ENABLED = false`. It implemented the authorization request, callback and state validation, private `chrome.storage.session` token confinement, exact-origin reads and an account check, but nothing in the extension imported it, and no Blackboard binding could reach it. The reason the exchange stayed disabled is a documentation limit, not an implementation gap: Blackboard documents 3LO with PKCE, but its public documentation does not establish that a public client inside a browser extension can complete the token exchange at `POST {origin}/learn/api/public/v1/oauth2/token` without an application secret. The documented fallback, Basic OAuth, requires an application key and secret pair, and a secret must never ship in an extension or enter Morrow's local configuration. No tenant has proved the secret-free exchange with a registered redirect URI, so the module could never return a connected session. Per Braden's direction, Blackboard connects through the official Anthology REST API in the Morrow app, so the module and its test were removed from the source tree and from the packaged Bridge file list in `scripts/package-mcp-bundle.mjs` on 6 September 2026. The Bridge now carries no Blackboard module and no browser token exchange, and connecting a Blackboard-looking tab returns an explicit refusal that names the REST connection instead. That refusal sends nothing to the site, saves no connection, and gives back the Chrome access the person had just allowed for it, because trying again cannot change the answer; `scripts/test/blackboard-browser-route.test.mjs` runs it. Restoring a browser path needs new external evidence first: an installed tenant application with End User Access that completes the PKCE exchange without a secret. The full browser contract, including the published-binding and refusal tables, stays in [blackboard-recovery-contract.md](../research/blackboard-recovery-contract.md). Sources: [Blackboard 3LO](https://docs.blackboard.com/docs/blackboard/rest-apis/getting-started/3lo), [REST and Learn](https://docs.blackboard.com/docs/blackboard/rest-apis/getting-started/rest-and-learn), and [Basic authentication](https://docs.blackboard.com/docs/blackboard/rest-apis/getting-started/basic-authentication).

One Morrow at a time holds the Bridge. The port is fixed at `127.0.0.1:32147` on both sides (`connector/extension/src/service-worker.js`, `packages/canvas-connector-mcp/src/config.ts`), so every assistant that uses one Morrow installation shares its one Chrome connection. A second Morrow, started from another project or another installation, cannot take the port. Close the other Morrow, or use one Morrow for all your assistants." with `components.extensionBridge.problem.code` set to `bridge_port_in_use`. When that Morrow closes, the waiting connector takes the port within a few seconds, so the person does not start the second Morrow again.

`EADDRINUSE` proves only that the port is taken. The message names the cause that produces it in practice; another program holding port 32147 would produce the same state. The popup and the setup guide state the rule as a constraint, not as a live state: the Morrow that cannot bind never reaches Chrome, and the Morrow that holds the port answers Chrome normally, so the extension has no separate signal for this condition and keeps reporting the connection it actually has.
