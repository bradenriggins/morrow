# Proven Canvas workflow reuse matrix

Updated: 2026-09-08

This is the implementation map for moving proven behavior into the current Morrow Bridge and MCP design. It records behavioral contracts that Morrow now uses or should add. It does not restore the legacy extension runtime, its session/token machinery, its stored state, its test profile, or any ExamplePlatform credential path.

## Evidence boundary

| Evidence label | Meaning |
| --- | --- |
| **Legacy worker proof** | A dated result recorded in the full legacy Morrow tree at commit `7275bfbc1c24dd6baff58f9435f1ce5a50fbb5d4`. It is useful donor evidence. It is not a fresh result for this release. |
| **Current Bridge test** | A local or synthetic test of the current Bridge and MCP source. It proves the contract code and its failure handling. It does not prove a provider effect. |
| **ExamplePlatform VPS test** | A test run through SSH on `example-lms-vps` against `/opt/example-attestation-repo`. It is evidence for a reusable control contract. It does not authorize or prove a new Canvas write. |
| **Live provider proof** | A fresh, exact provider read after a dispatched change. No row below gains this label from this matrix alone. |

A catalog row becomes a usable workflow only when it has all of the following:

1. One current source binding and one exact target.
2. A bounded plan that the user can review.
3. A single dispatch path with replay and unknown-outcome handling.
4. A fresh, operation-specific provider readback that proves the requested result.
5. A result that preserves partial success rather than retrying a completed first step.

## Largest site request families

These families name a user, group, section, account, folder, or global object instead of a direct course path. They are not candidates for a generic extra `course_id` input. They are site requests: each acts on the connected Canvas site as the signed-in person, Canvas decides it with that person's own roles, and it carries `authority.scopeClass: "site"`. [CANVAS-ADMISSION-CLASSES.md](CANVAS-ADMISSION-CLASSES.md) names each site class and its sentence. What each family still needs is an exact readback, listed below.

| Site family | Route shape | Next implementation step |
| --- | --- | --- |
| Users | Account and user session operations, and the three `/users/self/course_nicknames/...` routes. A nickname changes one person's own name for a course. | Add exact readbacks for the user routes the planner cannot read back. |
| Group discussions | `/groups/{group_id}/discussion_topics/...`. A group's own topic create and update stay course requests proved through the selected course's group list; every other group discussion route is a site request. | Add exact readbacks for entry, read-state, and subscription routes through the learner privacy boundary. |
| Files | Folder copy, the folder object itself, the file word count and link verifier, and account, group, and user file routes. Every upload first step waits for the reviewed transfer. | Extend the reviewed file transfer to folder, group, section and user uploads, and add readbacks for the copy routes that name their new object. |
| LTI registrations | Account-level application and LTI registration routes under `/v1/accounts/...`. The routes under `/lti/` stay held for the LTI tool's own authorization. | Add LTI client-credentials authorization for the `/lti/` service routes. |
| Section submissions | `/sections/{section_id}/...` grading and submission state, a learner-record site request. | Add learner-tokenized readbacks that compare the exact submission fields. |
| Outcome groups | Account and global outcome routes are site requests in the account class. Canvas decides them with the signed-in person's account roles. | Add exact readbacks where the planner has none, and an outcome-aware reader for the six OutcomeLink creates. Do not infer authority from a course that references an outcome. |
| Groups | Group membership and group objects, as learner-record and shared-object site requests. | Add readbacks for membership changes through the learner privacy boundary. |
| Conversations | Canvas Inbox routes do not encode a course, so they are site requests in the personal class. The private conversation adapter above stays available beside them. | Add exact readbacks for the raw routes that still have none. |
| Provider credentials and one-time actions | These routes create a sign-in credential, short-lived session, reset action, or error report. They are site requests in the session-credential class. Canvas keeps no exact field that Morrow can read after the request. | Report each one as sent with no exact readback, and keep every returned credential out of the result. |

## Readback work that remains

225 of the 541 admitted writes have no exact generic postcondition. They are profile-limited and are not callable in either full profile. They are not all the same problem: 184 have no safe read route at all, 30 are stopped by a named blocker, and 11 have a read with no exact target or postcondition. `readback.admittedWritesWithoutExactReadback` in the generated report lists all 225 by tool name.

| Gap | Count | Current state | Exact recommendation |
| --- | ---: | --- | --- |
| No safe generic read route | 184 | Canvas has no read of the written object, its created child, or the collection that holds it. | Add a named comparator per operation, only where Canvas has a source-proven postcondition on the written object. A bulk operation needs a per-child result set and a readback for every changed child. Until then keep the capability profile-limited and refuse it before provider I/O. |
| Favorite list is effective, not explicit, state | 2 | Canvas returns the effective favorites list, so adding or removing one course cannot be told apart from the default list. | Add support only if Canvas exposes the explicit favorite record for one course. Otherwise leave both writes unconfirmed. |
| Content migration update has no cataloged fields | 1 | The catalog exposes no changed field on `canvas_update_content_migration_courses`, so there is nothing to compare. | Model the migration fields in the catalog first, then compare the exact migration record. |
| External tool update has no cataloged fields | 1 | The catalog exposes no changed field on `canvas_edit_external_tool_courses`. | Model the external-tool fields in the catalog first, then compare the exact tool record. |
| Student grade or submission state | 9 | A grade, provisional grade, submission read state, rubric assessment, or submission comment changes a learner's own record, and the reads that show it return learner data the generic comparator does not tokenize. | Add a learner-tokenized comparator that reads the exact submission field and compares it through the learner vault. |
| Discussion or conversation content | 7 | Deleting an entry, subscribing, or changing read state changes learner discussion content or per-person state that the generic reader cannot compare. | Add comparators for the exact entry or subscription field, read through the learner privacy boundary. |
| Course delete or conclude is ambiguous | 1 | `canvas_delete_conclude_course` deletes or concludes the course by its event field, and the course read cannot tell a concluded course from a deleted one's saved state. | Split the two events into separate reviewed operations with their own postconditions. |
| Module item reader mutates progress | 1 | Reading a module item to confirm done state records progress for the reader. | Read module progression through a reader that does not record progress. |
| Module progression state has no current user reader | 1 | Relocking module progressions has no read of the progression state for the affected learners. | Add a learner-scoped progression reader before admitting the readback. |
| Outcome link identity is nested | 6 | A group's OutcomeLink list is keyed by the linked outcome, not by the group id the route names, so the generic collection reading would match the wrong record (ledger row 412). | Add an outcome-aware comparator that finds the created link by its outcome id. |
| Summary state has no narrow reader | 1 | Disabling a discussion summary has no read that returns the summary setting by itself. | Add support only after Canvas exposes the summary setting on a topic read. |

The shared rule is simple: `supportsReadback` may be true only when the actual planner can return a target or requested-field comparator and its evaluator has a focused test. A successful POST, PUT, DELETE, or a generic response object is not a verified result.

## Delivery order

1. Finish the Canvas Inbox MCP planner and end-to-end synthetic transport test. It is a narrow, high-value workflow whose direct adapter already has strict recipient and reply checks.
2. Keep the Page/Assignment-to-Module composed batch path bound to the verified first-child result. Extend it only through its immutable result-binding schema.
3. Use the existing reviewed file transfer for course-file creation. Add no generic file mutation support until a fresh course-owned object resolver and exact file readback contract exist.
4. Define an administrative authority contract for account, user, global, and LTI workflows: exact current context, approval class, affected-subject and data policy, single-send behavior, and operation-specific readback. The account, global, LTI registration, and developer key part of that contract is written in [CANVAS-ADMISSION-CLASSES.md](CANVAS-ADMISSION-CLASSES.md). Implement one bounded workflow at a time.
5. Add group and section resolvers only after a source-proven ownership relation and privacy policy are defined.
6. Add operation-specific readback comparators in the highest-value course workflows before expanding their public capability claims.
