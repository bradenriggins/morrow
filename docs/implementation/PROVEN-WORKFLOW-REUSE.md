# Proven Canvas workflow reuse matrix

Updated: 2026-09-08

This is the implementation map for moving proven behavior into the current Morrow Bridge and MCP design. It records behavioral contracts that Morrow now uses or should add. It does not restore the legacy extension runtime, its session/token machinery, its stored state, its test profile, or any ExamplePlatform credential path.

## Evidence boundary

| Evidence label | Meaning |
| --- | --- |
| **Legacy worker proof** | A dated result recorded in the full legacy Morrow tree at commit `7275bfbc1c24dd6baff58f9435f1ce5a50fbb5d4`. It is useful donor evidence. It is not a fresh result for this release. |
| **Current Bridge test** | A local or synthetic test of the current Bridge and MCP source. It proves the contract code and its failure handling. It does not prove a provider effect. |
| **ExamplePlatform VPS test** | A test run through SSH on `example-lms-vps` against `/opt/example-attestation-repo`. It is evidence for a reusable control contract. It does not authorize or prove a new Canvas write. |
| **Live provider proof** | A fresh, exact provider read after a dispatched change. No row below gains this label from this matrix alone. |

A catalog row becomes a usable workflow only when it has all of the following:

1. One current source binding and one exact target.
2. A bounded plan that the user can review.
3. A single dispatch path with replay and unknown-outcome handling.
4. A fresh, operation-specific provider readback that proves the requested result.
5. A result that preserves partial success rather than retrying a completed first step.

## Largest remaining course-scoping families

The following held families are large because their API routes name a user, group, section, account, folder, or global object instead of a direct course path. They are not candidates for a generic extra `course_id` input. Account, user, global, and LTI workflows remain part of the product scope, but each needs a distinct authoritative context, approval class, subject-data policy, and exact readback contract before admission. Every account, global, LTI registration, and developer key write is held with the reason `account_authority_required` and carries `authority.scopeClass: "account"`; [CANVAS-ADMISSION-CLASSES.md](CANVAS-ADMISSION-CLASSES.md) holds that contract.

| Held family | Held writes | Route shape and decision | Safe resolver direction |
| --- | ---: | --- | --- |
| Users | 24 | Twenty-one are account or user session operations and require non-course authority. The three course-nickname routes use `/users/self/course_nicknames/...`. A nickname changes one person's own name for a course, not anything inside the course, so all three are held with the reason `self_scope_not_supported`. | Keep the course-nickname routes held. Morrow changes content inside a selected course; it does not change a personal Canvas preference. For account or user operations, define the separate current-account context, approval class, affected-subject policy, and exact readback before admission. |
| Group discussions | 22 | All held routes are `/groups/{group_id}/discussion_topics/...`. A group can be outside the selected course. | Freshly discover the group through the selected course’s authoritative group relation, freeze group ID and course proof, then permit only the exact group discussion route. Reject user groups, missing ownership, and stale proof. |
| Files | 14 | Renaming, moving, and removing a course file, and adding a folder inside a course folder, are now admitted through the course-ownership reading in `packages/canvas-api-catalog/src/semantic-target.ts`. The held set is the rest: folder copy and upload, the folder object itself, the file word count and link verifier, and the account, group, and user file routes. | Keep them held. Each one either reaches a second object that the reading of the first proves nothing about, as both copy routes do, or has no course-ownership reading declared for it yet. Account, group, and user file routes need their own authority, not this reading. |
| LTI registrations | 16 | All are account-level application or LTI registration routes, held with the reason `account_authority_required`. | A course resolver would not create account authority. Define the current-account or current-LTI context, approval class, affected-course and data policy, and exact readback contract before admission. |
| Section submissions | 14 | All held routes are `/sections/{section_id}/...` and include learner-sensitive grading or submission state. | Add no broad resolver. Consider a narrow workflow only after a fresh selected-course section read proves section ownership and the learner/data authorization is separately satisfied. Bind the section, assignment, and subject identity to one operation. |
| Outcome groups | 14 | Account and global outcome routes are not course routes. Both are held with the reason `account_authority_required`. | Define an account/global authority context and approval contract before admission. Do not infer authority from a course that references an outcome. |
| Groups | 13 | Group membership and group-content routes can name cross-course or user-owned objects. | Share the exact course-owned group resolver with group discussions only after the requester and affected-member privacy checks are explicit. |
| Conversations | 8 | Canvas Inbox routes do not encode a course. | Use the dedicated private conversation adapter above. Do not admit the generic catalog operations. |
| New Quizzes Item Banks | 9 | All nine writes are held. Bank creation lacks a recoverable create-and-course-associate transaction. Existing-bank mutations lack complete downstream reach. The selected-quiz bank draw lacks durable recovery after a worker or process interruption. | Keep every Item Bank write, including image alternative-text repair and the bank draw, held before provider I/O until the missing proof exists. |

## Readback work that remains

82 of the 245 admitted writes have no exact generic postcondition. They are not all the same problem: 59 have no safe read route at all, and 23 are stopped by a named blocker. `readback.admittedWritesWithoutExactReadback` in the generated report lists all 82 by tool name.

| Gap | Count | Current state | Exact recommendation |
| --- | ---: | --- | --- |
| No safe generic read route | 59 | Canvas has no read of the written object, its created child, or the collection that holds it. `canvas_reset_course`, `canvas_create_score`, and `canvas_delete_rubricassociation` are in this group: their nearest read describes a different object, so the planner returns nothing instead of proving the wrong thing. | Add a named comparator per operation, only where Canvas has a source-proven postcondition on the written object. A bulk operation needs a per-child result set and a readback for every changed child. Until then keep capability readback false and the result unconfirmed. |
| Student grade or submission state | 9 | Marking a submission read or unread, clearing unread status for all submissions, selecting provisional grades, deleting a submission comment or a rubric assessment, and resetting what-if scores have no narrow reader for the exact state. | Add a dedicated reader only where Canvas exposes the exact state on the selected submission. Bind course, assignment, user, and item IDs, and satisfy the separate learner-data authority first. |
| Discussion or conversation content | 7 | Topic and entry read state, subscription state, entry deletion, and conversation message feedback have no reader for the requested state. | Add per-action readers that compare the specific topic, entry, subscription, or feedback field. For deletion, require exact absence from a complete collection or a direct 404. |
| Favorite list is effective, not explicit, state | 2 | Canvas returns the effective favorites list, so adding or removing one course cannot be told apart from the default list. | Add support only if Canvas exposes the explicit favorite record for one course. Otherwise leave both writes unconfirmed. |
| Content migration update has no cataloged fields | 1 | The catalog exposes no changed field on `canvas_update_content_migration_courses`, so there is nothing to compare. | Model the migration fields in the catalog first, then compare the exact migration record. |
| External tool update has no cataloged fields | 1 | The catalog exposes no changed field on `canvas_edit_external_tool_courses`. | Model the external-tool fields in the catalog first, then compare the exact tool record. |
| Module item reader mutates progress | 1 | The only Canvas read that returns module-item completion marks the item as viewed, so reading would change what it measures. | Use a course-level progression read that does not mutate, or leave the outcome unconfirmed. |
| Module progression has no current-user reader | 1 | Re-locking module progressions has no read that returns the current user's progression state. | Add support only after Canvas exposes a progression read for the acting user. |
| Summary state has no narrow reader | 1 | Disabling a discussion summary has no read that returns the summary setting by itself. | Add support only after Canvas exposes the summary setting on a topic read. |

The shared rule is simple: `supportsReadback` may be true only when the actual planner can return a target or requested-field comparator and its evaluator has a focused test. A successful POST, PUT, DELETE, or a generic response object is not a verified result.

## Delivery order

1. Finish the Canvas Inbox MCP planner and end-to-end synthetic transport test. It is a narrow, high-value workflow whose direct adapter already has strict recipient and reply checks.
2. Keep the Page/Assignment-to-Module composed batch path bound to the verified first-child result. Extend it only through its immutable result-binding schema.
3. Use the existing reviewed file transfer for course-file creation. Add no generic file mutation support until a fresh course-owned object resolver and exact file readback contract exist.
4. Define an administrative authority contract for account, user, global, and LTI workflows: exact current context, approval class, affected-subject and data policy, single-send behavior, and operation-specific readback. The account, global, LTI registration, and developer key part of that contract is written in [CANVAS-ADMISSION-CLASSES.md](CANVAS-ADMISSION-CLASSES.md). Implement one bounded workflow at a time.
5. Add group and section resolvers only after a source-proven ownership relation and privacy policy are defined.
6. Add operation-specific readback comparators in the highest-value course workflows before expanding their public capability claims.
