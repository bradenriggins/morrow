# Moodle full functionality scope

Status: active implementation scope.  
Target: complete Moodle LMS 5.2 core functionality through Morrow's signed-in browser bridge, at the same task level as Canvas.  
Baseline: the generated Moodle catalog is a partial checkpoint, not parity completion. Resource root-file metadata has focused and live signed-in proof. A historical text Multiple choice creation receipt has a verified provider result and independent native readback, but it does not establish a current capability: all Question bank creation and updates are now held before a native request. Exact package and live-overlay limits are recorded in the private preview receipt.

This document is the implementation and acceptance list for the directive: **ALL MOODLE FUNCTIONALITY BUILT IN, JUST LIKE CANVAS.** It covers Moodle core administration as a target. It does not reduce scope to common educator tasks.

Dated bridge receipts and screenshots remain in [THREE-LMS-BRIDGE-PARITY.md](THREE-LMS-BRIDGE-PARITY.md). Do not duplicate their history here.

## Non-negotiable bridge contract

- Bind every request to one HTTPS Moodle site, installation subpath, signed-in principal, and exact course or system context.
- Keep Moodle session cookies, `sesskey`, draft IDs, file URLs, OAuth data, and secret form controls in Chrome. Do not return them through Morrow.
- Use a fixed, source-proven native form or same-site AJAX action. Do not use arbitrary URLs or caller-supplied form fields.
- Before every write, read the exact target and preserve protected native controls. Require a human review or an exact, active Edit permission selected by the user in the extension. Dispatch once, then read back the authoritative saved state. A dispatched mismatch or lost response is `applied_or_unknown`; it is never retried automatically. Edit permissions are an active implementation requirement, not current release proof.
- Treat native `view.php` routes as potentially effectful. An activity view can record completion, attendance, a launch, or other learner state. A read must use an established source that does not save course or learner state. Native settings reads can prepare private editor copies; disclose that behavior and keep the temporary identifiers internal.
- Enforce Moodle capabilities at the exact system, category, course, or module context. Do not infer authority from a role label. Moodle sites can override all standard roles and capabilities.

The current implementation already uses the signed-in page, validates the binding, keeps `sesskey` internal, and limits each approval to one dispatch. A workflow with several native effects must disclose and verify each effect. See [moodle-executor.js](../../connector/extension/src/moodle-executor.js) and [service-worker.js](../../connector/extension/src/service-worker.js). Moodle's Access API defines this context-and-capability model and requires course/activity login checks. [Access API](https://moodledev.io/docs/5.2/apis/subsystems/access)

### Activity copy, deletion, and exact placement

`moodle_duplicate_activity`, `moodle_delete_activity`, and `moodle_move_activity_to_position` use the same native course-format action endpoint the course page's own editing controls use, with the actions `cm_duplicate`, `cm_delete`, and `cm_move`. They are not restricted to the five module types of the move contract above: they accept an activity of any core module type, and a deletion additionally requires that Morrow can name the records that module removes. All three read the complete course state and the native course format, require the digest of the state the person reviewed, read the format and the state again immediately before dispatch, send one action, then require the complete course state back with exactly the approved change in it. A lost response, a state that is not the approved one, and a course format that is unreadable or different afterwards are all `applied_or_unknown`.

A position is a place in a list Morrow has read. Morrow takes the complete membership of the destination section, removes the moved activity from it, inserts it at the requested place, and sends the activity that now follows it as `targetcmid`, because Moodle inserts a moved activity immediately before that target and at the end of the section when there is none. This is the one operation here that can reorder an activity inside the section it is already in.

Deletion is `destructive: true` and `irreversible: true`, and Morrow has no route that restores any part of it. It is published for review every time instead of being offered as a standing Edit grant, so a person approves each deletion with the exact activity in front of them. Moodle takes the activity out of the course at once and removes its records and files with a background task. The result states the exact set the removal takes with it: the activity and its place in the section, every file in every one of its file areas, its grade item with every grade and feedback, its completion records, calendar events, tags, comments and ratings, and its role assignments and permission overrides, together with the learner records that module type keeps. Morrow refuses an activity whose module type is not in that enumerated set, which is every activity module a site installs itself, and it refuses a Question bank activity, because removing one removes its categories and the questions in them.

A copy carries the activity's settings, content, and every file it stores. It carries no learner submissions, attempts, responses, or grades, because Moodle copies an activity by running the single-activity backup with user data switched off. The copy keeps the original's visibility, so a copy of an activity learners can see is visible to learners as soon as it is created. Moodle assigns the copy's ID and names it in the site language, so those two fields are read from the saved state. The copy's module type, section, visibility, stealth, restriction, and access fields must match the original, the copy must sit immediately after the original in the section, and every other activity, section, and section order must be unchanged. Fields Moodle derives from the new ID, such as the copy's own address, are not compared.

Refused before the first native request: an activity that delegates a subsection, an activity inside a section Moodle owns, a course whose native settings form does not report `topics` or `weeks`, and, for a copy or a placement, a hidden, stealth, or access-restricted activity or section. The browser fixture drives Chrome against a local server serving Moodle's own state and course-settings responses. It proves the digest agreement with `moodle_get_contents`, one action per operation, the exact `targetcmid` for a first, middle, and last position, the enumerated removal set, every refusal above with no action sent, an unrelated change made during the action, a copy that does not carry the original's visibility, a lost response after dispatch with no second send, and a course format that changes under the action. This is fixture evidence. No signed-in Moodle site has run any of these three operations. ### Section lifecycle

`moodle_create_section`, `moodle_delete_section`, and `moodle_move_section` use the same native course-format action endpoint as the activity lifecycle above, with the actions `section_add`, `section_delete`, and `section_move_after`. All three read the complete course state and the native course format, require the digest of the state the person reviewed, read the format and the state again immediately before dispatch, send one action, then require the complete course state back with exactly the approved change in it and the format unchanged. A lost response, a state that is not the approved one, and a course format that is unreadable or different afterwards are all `applied_or_unknown`.

Adding a section adds one empty visible section at the end of the course. Moodle's `section_add` without a target section appends, because `course_create_section` treats position 0 as the end, so nothing already in the course changes place; that also keeps the operation at `moodle/course:update` alone. Morrow does not name the new section and does not place it: `moodle_update_section` gives it a name and `moodle_move_section` puts it somewhere else, each as its own approved change. The new section must come back empty, visible, unrestricted, and last, with every other section, activity, and section order unchanged.

Moving a section takes a place in the course order, counting from 1, and turns it into the exact section Moodle must put the moved one after, taken from the complete order Morrow has just read. It requires `moodle/course:movesections`. Moving renumbers every section between the old and the new place. The General section is place 0; Moodle does not move it, and Morrow refuses a place that is not a place in that order and a place that leaves the order as it is.

Deleting a section is `destructive: true` and `irreversible: true`, and it requires `moodle/course:update` with `moodle/course:movesections`. Moodle's `section_delete` removes every activity in the section and then deletes the section with the force flag, so a section that is not empty is deleted with its contents, and the records and files go with a background task. Morrow has no route that restores any of it. It is published for review every time instead of being offered as a standing Edit grant. The complete course state the person reviews lists every activity in the section, and the result names each one with the records its module type removes. Refused before the first native request: the General section, which Moodle does not delete, a section holding a Question bank activity, because removing one removes its categories and the questions in them, and a section holding an activity module a site installs itself, whose removed records Morrow cannot name.

Moodle builds four things from a section's place: the shown title of a section that has no name of its own, the current-section flag, the link to the section, and the course's highlighted name. A deletion and a move change the place of every later section, so for a section whose place changes those four are the only fields Morrow does not require back unchanged. Every stored section name, summary flag, visibility, restriction flag, and activity list, the complete section order, the section count, and every activity in the course must come back exactly as planned. All three operations refuse a course that holds a section Moodle itself owns or an activity that delegates one, because renumbering would move a subtree Morrow has not read, and they refuse a course whose section numbers, section list, and section membership are not the one order Morrow read.

A section's name and summary stay with `moodle_update_section`, which writes the section's own native settings form. That form also holds the section's access restrictions, in the single `availabilityconditionsjson` control of `course/editsection_form.php`. Morrow does not write restrictions there: the write names the `name` and `summary_editor[text]` controls alone, and every other control of the form, the restrictions included, goes back to Moodle exactly as it was read, under the protected digest that covers them. So a restriction the section already holds survives a rename, a restriction that changed between the review and the change refuses the reviewed digest, a restriction that changed between the form Morrow prepared and the moment it would send stops the write before it is sent, and a restriction changed by something else while the change was applied leaves the result unverified. Writing a restriction is a separate operation, `moodle_update_section_restrictions`, which writes that one control on the same form and carries the name, the summary and every other control through unchanged.

A second fixture serves the section's own native settings form and proves all four restriction outcomes above, with the sent POST carrying the section's restriction value back exactly as the form gave it. ### Subsections and delegated sections

A Moodle Subsection is an activity that owns a course section. `subsection_add_instance` inserts the activity record and then calls `formatactions::section($course)->create_delegated('mod_subsection', $id, ...)`, so one Save creates both the activity and the section shown inside the section that holds it. Everything below rests on reading that pairing in full before anything else: every section a component owns must be paired with exactly one activity that delegates it, that activity must sit in the section the owned section reports as its parent, that parent must itself be an ordinary section, and the owned section's activity list must be exactly the activities that name it. A pairing Morrow cannot state exactly, and any component other than `mod_subsection` that owns a section, refuse before any request that changes state. The state's own `itemid` never crosses the bridge, so the pairing is read from the section each activity names and the parent each section reports. Moodle does not let a subsection hold a subsection, so the contents of one subsection are one list, not a tree.

`moodle_get_subsection` returns one subsection's name and visibility, the owned section's number, stored name, shown title, visibility, summary flag and restriction flag, the section that holds the subsection, and how many activities it holds. `moodle_list_subsection_contents` adds every activity in the stored order of the owned section, with its ID, name, module type, visibility, stealth state, learner access and restriction flag. Both read the course state through the same native `core_courseformat_get_state` route as `moodle_get_contents`, and neither opens `/mod/subsection/view.php`, which records a module view and a completion state. Seeing a hidden subsection needs `moodle/course:viewhiddensections` at the course context.

`moodle_create_subsection` adds one hidden subsection through the native `course/modedit.php` form for `add=subsection`, with the form's own `visible` control set to 0. It requires `moodle/course:manageactivities` with `mod/subsection:addinstance`. Moodle gives the section it creates the same name and the same hidden state as the activity, and `calculate_positions` places a section that carries a component after the course's last section number with nothing moved afterwards, so no section already in the course changes place and the course's own last section number rises by exactly one. The create requires the reviewed digest of the complete course state, reads the native form, reads the state and the form again immediately before it sends, sends one POST, then requires the complete course state back with exactly one new hidden subsection and its one new hidden owned section added, the new activity at the end of the section it was added to, the new section last in the course's section list, and every other section, activity and section order unchanged. It writes a name and nothing else: no description, no files, no restrictions, and it never sends the form's own learner-notification control. It refuses a name carrying `<`, `>` or `&`, because Moodle rewrites those when it renders a name and the saved name is compared exactly.

The blanket delegated refusals in the move and visibility contracts are replaced by an exact contract that reads that complete pairing first. A move may take an activity out of, or put one into, the section a subsection owns, and a subsection may be moved between ordinary sections, carrying the section it owns and every activity in it; the result names each of those activities. Moodle itself refuses a subsection moved into a subsection (`stateactions::cm_move` throws `subsectionmoveerror`), so Morrow refuses that before anything is sent. The move keeps every other condition of the move contract, including a visible activity and a visible destination, so Moodle's own `update_visibility_in_section` cannot change a visibility this move never named.

A hide may reach a subsection: hiding the subsection activity, hiding the ordinary section that holds it, or hiding the section it owns. Moodle carries the change from the activity into the owned section and from there into every activity that section holds, through `cmactions::set_visibility` → `update_delegated` → `sectionactions::update` → `transfer_visibility_to_cms`, and hiding the owned section also hides the activity that delegates it. Morrow states every one of those activities in the result and requires each of them back hidden, with the owned section hidden and reporting no restriction, and the pairing still complete. A subsection whose own visibility and whose owned section's visibility already differ cannot be planned forward and refuses, and a change to an owned section that would leave it as it is refuses instead of sending an action whose effect Morrow cannot state.

A show is refused whenever it would restore a stored visibility. `transfer_visibility_to_cms` puts each activity back to the `visibleold` Moodle stored before the subsection was hidden, and the course state does not carry that value, so Morrow cannot state the result. The one exception is showing a subsection that holds no activity: `transfer_visibility_to_cms` returns before it touches anything when the section's sequence is empty, so the owned section simply becomes visible and nothing is restored.

It proves the read, the ordered contents list, one POST per create with the complete state delta and the digest agreement with `moodle_get_contents`, an activity moved into an owned section, a subsection moved between ordinary sections with its owned section's parent updated and every carried activity named, a hide of the subsection, of the section that holds it and of the section it owns with every reached activity hidden and named, the empty-subsection show, and every refusal above with nothing sent: the incomplete pairing, the unknown owning component, the nested move, the restoring show, the mismatched pair, the unchanged owned section, a stale digest, a rewritten name, a subsection parent, and a form control that changed between the review and the send. ### Group and grouping lifecycle bounded evidence

Nine writes and one further read reach the group surface, and every one of them uses a native page of Moodle's own group management, each of which calls `require_capability('moodle/course:managegroups')` at the exact course context before it does anything. `moodle_get_course_groupings` reads the groupings page and then each grouping's own group-assignment page, both plain GETs that reach none of their own action branches, and returns each grouping's ID, name, activity count and exact group IDs with a digest over that reading. `moodle_create_group` and `moodle_update_group` post the native group form; `moodle_delete_group` posts Moodle's own delete confirmation; `moodle_add_group_member` and `moodle_remove_group_member` post the native member form with Moodle's own add or remove control and one user; `moodle_create_grouping` and `moodle_update_grouping` post the native grouping form; and `moodle_set_grouping_groups` posts the grouping's own assignment form. `moodle_set_activity_group_mode` is not one of them: it uses the same `core_courseformat_update_course` action the course page's group-mode control uses, which requires `moodle/course:manageactivities`.

Two Moodle rules bound what these writes can do, and both are taken from Moodle's own state rather than from a role label. Moodle freezes a group's visibility and participation controls as soon as the group has one member, so a change to either is refused while the loaded form holds them frozen, and every membership change reports the visibility the group already has, because adding a member to a hidden-membership group does not make that member visible to other learners. A course can force its own group mode on every activity, and that forced mode overrides the value an activity stores, so the activity group mode reads the course setting as well and reports both the value it saved and the mode that is in effect.

Each group write reads the course group list, and each grouping write reads the complete grouping state, immediately before it acts; a grouping write also requires the digest of the reading that was reviewed. Each one sends exactly one POST and then requires the authoritative saved state back with exactly the approved change in it and every other group, grouping and control unchanged. A lost response, a saved state that is not the approved one, or a change to a control the write did not name is `applied_or_unknown`, and none of them is retried. A native form that refuses its own input renders itself again and saves nothing; that is reported as `moodle_form_validation_failed`, a refusal, not an unknown outcome. `moodle_delete_group` is destructive and irreversible: it reads the group's complete saved membership first, lists every member the deletion removes, and refuses when that membership is not the membership the approval named. Member identities cross the normal Moodle roster privacy boundary and leave only as stable learner tokens.

Bounds are refusals, never truncations or guesses. A member is added only when Moodle's own member form lists that user as a candidate for that exact group; Moodle stops listing candidates when the course holds more of them than its user-selector limit, which is 100 by default, and Morrow then returns `moodle_group_member_list_bounded` instead of sending a change it cannot bind. Moodle's grouping form adds or removes in one submission and never both, so a requested group set that needs both directions is refused as two changes. A name carrying `<`, `>`, `&`, `"` or `'` is refused, because Moodle escapes a stored name for display and the saved value could not then be compared with the requested one. Group descriptions, ID numbers, enrolment keys and pictures are carried through the form unchanged and cannot be set here.

#### Dedicated hidden Question bank isolation research

This is source research only. It does not enable a bridge operation or weaken the current Question-bank hold.

In unmodified Moodle 5.2.2 core, a newly created standard `mod_qbank` activity can provide an isolated new-question context. Its form forces `visible = 0` and `type = standard`; its instance callback creates the `qbank` record. The Question bank view resolves the activity's module context, and `question_edit_url()` lazily creates a top category and a default child category in that exact module context. A newly created default category therefore has a new global category ID and a fresh module context. [Qbank form](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/mod_form.php#L30-L94), [Qbank instance](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/lib.php#L52-L68), [Qbank context route](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/view.php#L26-L32), [default category](https://github.com/moodle/moodle/blob/v5.2.2/public/lib/questionlib.php#L1077-L1119).

For a standard core random slot with the default positive category filter, a fresh category is outside that slot's prior category selection. A direct `question_references` row has a foreign key to one existing `question_bank_entries` record, so it cannot name a Question-bank entry that does not yet exist. A random `question_set_references` row has no Question-bank-entry field. It instead records `questionscontextid` and JSON `filtercondition`. Native random-slot creation requires an existing category filter and saves that category's current context. The core category filter compiles that default filter to `qbe.questioncategoryid` equal to its saved category IDs, and recursive expansion traverses child categories only in the saved category's context. The random loader combines those filters and then selects the latest ready version. It does not expand a positive old-category filter to a future module context or a new root category. [Reference schema](https://github.com/moodle/moodle/blob/v5.2.2/public/lib/db/install.xml#L1514-L1550), [random-slot validation and persistence](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/quiz/classes/structure.php#L1680-L1745), [category filter](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/managecategories/classes/category_condition.php#L145-L167), [same-context descendant traversal](https://github.com/moodle/moodle/blob/v5.2.2/public/lib/questionlib.php#L1180-L1213), [random loader](https://github.com/moodle/moodle/blob/v5.2.2/public/question/classes/local/bank/random_question_loader.php#L121-L185).

This is not sufficient isolation. Core permits a category filter with `jointype = NONE`; the same category filter then compiles to `NOT IN`. The normal random-slot validator requires only a category filter, not positive membership. Such a core random reference that excludes an old category can select the fresh Qbank category. An addition or update in an existing category can also match a pre-existing random filter because the loader selects current ready versions dynamically. Installed Question-bank plugins add further filter classes. Morrow must reject this route when it cannot inventory and recognise every enabled filter class, when it cannot enumerate and parse every stored random filter, when a stored random filter is malformed or lacks the native category contract, or when it cannot establish the new Qbank module context and default category by fresh native readback. #### Hidden Question bank isolation, phase one

Morrow implements effects one and two of the table above as two separate approved changes. Each has its own review read, its own single native dispatch, and its own authoritative readback. Neither creates a question and neither changes a Quiz, so the deterministic Question-bank hold stays in force and every result repeats that.

`moodle_create_qbank_activity` creates one hidden `mod_qbank` activity with the reviewed name in the approved course and section, through the native `/course/modedit.php` form with `add=qbank` and Save and return to course. It requires `moodle/course:manageactivities` at that course context. `moodle_get_qbank_activity_creation_form` is its review read. Morrow requires the core Qbank form: `modulename` `qbank`, `type` `standard`, `visible` `0`, one name field, one empty description editor and its one draft area, and the `submitbutton2` control. It refuses a form that declares a file manager, a file picker, or any other draft file area, a form action that carries a query or another origin, a form that names another session, and a form whose module type is not core Qbank. It reloads that form immediately before sending, sends one POST that preserves every other native control, then reads the saved course state and the saved module form back and requires exactly one new module in the approved section with the reviewed name, `visible = 0` and bank type `standard`. A new course module always has its own new module context, and this action does not open the Question bank, so it reports the bank context as not established. [Qbank form](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/mod_form.php#L30-L94), [Qbank instance](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/lib.php#L52-L68)

This is a separate approved change because `/mod/qbank/view.php` takes the module context of the module it is given and calls `question_edit_url()`, which calls `question_get_default_category` with creation enabled: Moodle creates the context's top category and its default child category, with no capability check of its own, and then returns `/question/edit.php?cat=<categoryid>,<contextid>&cmid=<cmid>`. It also requires the page's own category filter list to show exactly one context group, so no listed category leaves the new module context. Without the add control, or with more than one context group, Morrow refuses to bind the category and reports the change as applied, because the dispatch already realized it. [Qbank context route](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/qbank/view.php#L26-L32), [default category](https://github.com/moodle/moodle/blob/v5.2.2/public/lib/questionlib.php#L1077-L1119), [add-question control](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/editquestion/classes/plugin_feature.php#L57-L70)

The remaining limits are exact. These two effects do not establish isolation on their own: they create the bank and its category, and the two effects in the next section are what put one question in it. The `moodle/question:add` check happens in the readback, after the dispatch that realizes the category, because no native route exposes that capability at a new module context without also creating the categories. A site that requires an activity description refuses this creation, and Morrow reports the native validation page as a change that saved nothing. #### Hidden Question bank isolation, phase two

Morrow implements effects three and four of the table above as two more separate approved changes. Each has its own review read, its own single native dispatch, and its own authoritative readback. Both re-derive the course's complete Question bank impact scope first, with the rules and the recognised filter set of `moodle_get_question_bank_impact_scope`, and refuse unless that scope is complete. A stored random filter with `jointype = NONE` has its own refusal, because that filter compiles to a `NOT IN` category test that a fresh category can satisfy.

`moodle_create_qbank_question` creates one new `truefalse` or `shortanswer` question in the approved bank category. `moodle_get_qbank_question_creation_form` is its review read. Morrow starts at the approved bank page, `/question/edit.php?cat=<categoryid>,<contextid>&cmid=<cmid>`, and requires its add-question control, which is how `moodle/question:add` at the bank context is visible to a browser. It follows that control's own chooser, `/question/bank/editquestion/addquestion.php`, to the native question controller, and requires a creation form: no question ID and no copy control, the approved category and question context, status `ready`, no file manager, file picker or file input, an empty rich-text value for every draft area the form carries, no selected tag, and a return address on the bank page with no `appendqnumstring`, which is the parameter that would make the same native chain add a Quiz slot in the same request. It reloads that form immediately before sending, sends one POST that preserves every other native control, then reads the bank page and the saved entry back. It requires exactly one bank entry that the bank page did not list before the POST, and requires that entry's ready version, name, question text, answers, feedback, category and question context to equal the approved values. It never updates, clones or moves a saved entry, and it adds no Quiz slot. [Question controller](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/editquestion/question.php#L109-L185), [save path](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/editquestion/question.php#L254-L304), [add-question control](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/editquestion/classes/plugin_feature.php#L57-L70)

After the one dispatch Morrow reads the saved Quiz structure back and requires exactly one new slot at the end, with a direct reference to the approved entry, the latest-version mode, and every earlier slot unchanged. The native reference is `version = NULL`, so every later edit to that entry stays held, and every result says so. [Quiz add action](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/quiz/edit.php#L98-L107), [direct-slot write](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/quiz/locallib.php#L1742-L1895)

Neither one opens a Quiz view, attempt, review or report page, so neither records learner state, and no result carries a session key, a draft item ID or any learner identity.

The remaining limits are exact. Only `truefalse` and `shortanswer` are supported, because they are the simplest native forms with no file area. Creation in an existing category, every question update, and every question file or tag stay held. A site with third-party Question bank filter plugins is not proved safe: an unrecognised stored filter keeps the impact scope incomplete, which refuses both effects, and that is the only protection Morrow has there. A lost response after either dispatch is `applied_or_unknown` and is never retried. Browser-fixture proof only; no signed-in Moodle site has run either effect.

#### Installed Question Bank filter-inventory limit

Moodle's Question Bank administration page cannot be used as a teacher-side precondition. The plugin toggle controller requires a site administrator before it returns to `/admin/settings.php?section=manageqbanks`. The native Question Bank UI does expose an effective filter list in its rendered hidden data source, but that list contains only each filter key, title, required flag, and optional JavaScript filter class. It does not expose the server-side PHP condition class or the Question Bank plugin component. Those identifiers are available only to Moodle's server-side dynamic plugin discovery. A custom enabled plugin can therefore replace a known key with a different PHP condition while the browser-visible inventory remains indistinguishable. [Admin controller](https://github.com/moodle/moodle/blob/v5.2.2/public/admin/qbankplugins.php#L29-L72), [browser filter export](https://github.com/moodle/moodle/blob/v5.2.2/public/question/classes/output/question_bank_filter_ui.php#L88-L141), [server-only condition discovery](https://github.com/moodle/moodle/blob/v5.2.2/public/question/classes/local/bank/filter_condition_manager.php#L64-L80).

`moodle_get_question_bank_filter_inventory` only inspects an already-open native Question Bank page. It never navigates or submits a Moodle request for that page. Its result explicitly marks the condition-class and plugin-component facts as not exposed and Qbank isolation as ineligible. This supports diagnosis but cannot enable any Question Bank creation, update, category realization, or Quiz-slot attachment. The existing deterministic Question Bank hold remains in force.

#### Question Bank impact scope

`moodle_get_question_bank_impact_scope` enumerates the stored Question Bank references of one exact selected course. It reads the native course state service and each Quiz edit page only. It never opens `/mod/quiz/view.php`, `attempt.php`, `review.php`, or `report.php`, so it records no completion, attempt, or report event. It requires `mod/quiz:manage` at each Quiz module context, which is what Moodle requires to open the Quiz edit page. It adds no write and unlocks none; the deterministic Question Bank hold stays in force.

For each slot it records the stored reference: a direct `question_references` entry with its question ID and version mode, or a random `question_set_references` entry with its `questionscontextid`, each stored filter key, each filter `jointype`, and whether the key is one Morrow recognises. Morrow recognises only the core category condition analysed above. It reads the stored random reference where the Quiz edit page carries it on the slot element as `data-filtercondition`, with `data-questionscontextid` or a `questionscontextid` field inside that JSON. Moodle renders random slots in more than one form across releases, and this reader recognises that pair and nothing else. [Reference schema](https://github.com/moodle/moodle/blob/v5.2.2/public/lib/db/install.xml#L1514-L1550), [random-slot validation and persistence](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/quiz/classes/structure.php#L1680-L1745), [category filter](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/managecategories/classes/category_condition.php#L145-L167), [random loader](https://github.com/moodle/moodle/blob/v5.2.2/public/question/classes/local/bank/random_question_loader.php#L121-L185), [bank usage query](https://github.com/moodle/moodle/blob/v5.2.2/public/question/bank/usage/classes/helper.php#L107-L136).

The result status is `impact_scope_incomplete`, with the exact reason for each affected Quiz and slot, when a stored filter key is outside the recognised set, a stored filter is malformed, a filter or its condition uses `jointype = NONE`, a Quiz or slot list is truncated, a random reference does not expose its questions context, or a direct slot reference cannot be resolved. The MCP boundary recomputes that verdict from the enumerated slots, so a browser result cannot report a complete scope that its own stored references contradict.

A complete status is bounded in three ways that are stated in every result. The browser cannot resolve a filter key to its server-side PHP condition class or plugin component, as the filter-inventory limit above records, so a site can replace a recognised key with a different condition and stay indistinguishable. The scope covers the approved course only and does not enumerate references from other courses. And a complete scope authorizes no Question Bank write: every Question Bank creation and update stays held. Browser-fixture proof only; no signed-in Moodle site has run it.

### Quiz attempt record, manual grading queue and regrade state

All three reads use one native entry point: a plain GET of `/mod/quiz/report.php` with a fixed `mode`, which is
how Moodle opens the report plugins under `public/mod/quiz/report/`. `mode=overview` is listed for a person who
holds `mod/quiz:viewreports`, and `quiz_grading_report::display()` calls `require_capability('mod/quiz:grade')`
before it renders the manual grading index, so the site enforces the capability at the exact module context. None
of the three opens `/mod/quiz/attempt.php`, `/mod/quiz/review.php`, or `/mod/quiz/reviewquestion.php`, so none of
them continues an attempt or records an attempt review. Each result names that route choice in its `proof` block.
The report route does record one `\mod_quiz\event\report_viewed` event for the signed-in teacher in the course
log; that is the one effect these reads have, and every result states it.

The regrade actions live on the same route. Moodle guards each one with `confirm_sesskey()` and
`mod/quiz:regrade`, so a request that carries neither a session key nor a regrade parameter cannot start a
regrade. Morrow sends neither, and the result proof states both. Moodle renders the only-regraded filter for a
person who holds `mod/quiz:regrade`; Morrow requires that filter on the page and refuses the read when it is
absent, rather than reporting zero regrade records for a person who cannot see them.

Moodle renders the attempt state, the started and completed times, and the duration through the language pack and
the reader's time zone. The attempt read resolves the state key from the report page's own state filter labels,
which carry the same language strings, and refuses the read when it cannot; it returns the three time values as
the exact text Moodle rendered and never parses them into an instant. Each question slot is read from the report
cell Moodle links to `reviewquestion.php`: the slot number and the question state come from that link and its
state class, and the mark is the number Moodle displayed, with the decimal separator of the reader's language
normalized. A slot the report shows without data is returned with no state and no mark. The read scans at most
ten report pages of 100 attempt rows and returns `moodle_quiz_attempt_incomplete` beyond that. Moodle applies the
reader's current group filter to this report and Morrow does not change it, so an attempt outside that filter is
reported as not found.

The manual grading index lists only questions that have a manually gradeable response, and Morrow asks for the
default view, which excludes questions graded automatically. Morrow requires the index heading that
`display_index()` renders before it reads counts, because a Moodle error page keeps the same page type and would
otherwise read as an empty queue. Each listed row's slot and question ID come from the grade links Moodle builds
for that row. Manual grading writes are not implemented, and running or committing a regrade is not implemented.
Moodle marks each regrade record as needed or done in language text with no machine-readable marker, so the
regrade read reports the record count and the pending-commit offer, not that split.

### Accessibility audit targets

`morrow_audit_course` reads one exact Moodle target at a time. It accepts these target kinds: `page`, `label`,
`url`, `forum`, `choice`, `book_intro`, `book_chapter`, `lesson_intro`, `glossary`, `wiki`, `feedback`,
`database`, `assignment`, `quiz`, `imscp`, `scorm`, `workshop`, `h5pactivity`, `glossary_entry`, `wiki_page`,
`lesson_page`, `feedback_item`, `database_field` and `quiz_question`. Each one reads the exact saved field
through the read route that already exists for it; `feedback_item` and `database_field` have no per-record
native read, so the audit reads the activity's own item or field list and keeps the one record whose saved ID
was selected, and refuses when that list does not name it exactly once.

The four source signals (an image with no alt text, a heading level jump, a table with no `th`, and embedded
media) are findings for a person to review. They are not a conformance decision, and a scan that returns no
signal is not a pass. Every Moodle audit result carries a `residual_coverage` block that states what the
selected target did not read: the manual checks source parsing cannot make at all (keyboard behavior, focus
order, contrast, captions, transcripts, equations, learner rendering), and the exact per-kind limit, such as the
Workshop submission and assessment instructions that the intro target does not read, the H5P package the
activity intro does not read, the Glossary attachment reported as present or absent only, the Wiki page history
and other groups' subwikis, the Lesson page answers and the file-bearing page the route refuses, the Feedback
question label and dependency, and the Database field description that Moodle's field list does not return.

Two fields named in this scope have no audit target, and each result and this row state why:

- **External tool (`mod_lti`) description.** `moodle_get_lti` reports only whether a description is set and never
  returns the description text, so there is nothing for a source scan to read. The tool itself runs on another
  site under another operator, and nothing the browser reads here describes what a learner reaches.
- **Forum posts.** Discussions and posts are learner-authored. They are read only through
  `moodle_get_forum_posts`, whose author identity is projected at the runtime privacy boundary; the audit's own
  source read is an internal call that receives the unprojected source envelope, so no audit target reads them.

No signed-in Moodle site has run any of these audit targets. Fixture proof only.

## Capability families

Do not hard-code “teacher,” “manager,” or “administrator” as permission checks. Use the native capability that Moodle evaluates in the target context.

| Work | Capability family |
|---|---|
| View a course or activity | Active enrolment or `moodle/course:view`, plus the module view capability and availability checks |
| Edit course or sections | `moodle/course:update`; course creation is category-level `moodle/course:create` |
| Add or manage activities | `moodle/course:manageactivities` and the module's `mod/<component>:addinstance` or manage capability |
| Manage files | Course or module file-management capability, plus repository policy |
| Grade | `moodle/grade:*`, grade-report capability, and module-specific grade/manage/release capability |
| Manage groups | `moodle/course:managegroups`; view rights can be narrower because membership visibility is protected |
| Review/manage enrolments and roles | Enrolment-plugin authority, `moodle/course:enrolreview`, `moodle/course:enrolconfig`, and applicable `moodle/role:*` capability |
| Question bank | `moodle/question:*` plus bank/category context capability and Quiz management capability where relevant |
| Backup and restore | `moodle/backup:*`, `moodle/restore:*`, and target course/category authority |
| Site administration | System-context administration or the exact delegated capability; secrets remain non-exportable |

## Required implementation order

1. Retain the verified Resource root-file metadata path as the starting point for the file workflow. Its catalog, executor, focused tests, and signed-in live proof agree.
2. Establish the exact native discovery and read contracts needed by each workflow as it is built. Extend the existing form, binding, review, and result checks. Do not delay complete workflows to build every read operation first.
3. Extend the verified single-file Resource and Folder workflows and the single-package IMS workflow to multiple files, existing files, editor attachments, and rich editors. Keep IMS navigation and learner launch outside file-byte verification. Question-bank writes remain held until random-reference impact discovery and authorization are complete. Both are dependencies for full resource, activity, question, feedback, and administration coverage.
4. Complete every resource and module lifecycle in the module table: create, read, edit, visibility, order, duplicate, delete, module-specific child data, files, and readback.
5. Complete Question bank and Quiz authoring, all 17 types, versions, dependencies, attempts, grading, feedback, and reports.
6. Complete learner and educator workflows: submissions, discussions, peer assessment, lessons, SCORM, H5P, LTI, conferencing, wikis, databases, feedback, and notifications.
7. Complete gradebook, enrolment, roles, groups, calendar, completion, restrictions, course lifecycle, import, backup, restore, copy, reports, and core administration.
8. Add installed-site plugin coverage only after an inventory of that site identifies each enabled optional component and its source, capability, form/action, file, external-effect, and verification contract.

This order is a dependency order. It does not remove later rows from the target.

### First staged file transfers

One approval covers one local file and one ordered draft upload plus a hidden Resource or Folder save. It binds the exact local file, filename, byte length, SHA-256, course, section, title, and creation-form digest. The native upload uses the repository and context options from that exact file manager. It does not assume a repository ID. After upload, Morrow verifies the draft bytes before submitting the module form. After save, it opens a fresh settings form and verifies the saved file bytes. An IMS package uses the native file picker, accepts one ZIP or IMS Common Cartridge, rejects an archive without a root `imsmanifest.xml` before upload, and verifies its saved backup bytes after its hidden save. It never opens the IMS package view; byte equality does not establish package navigation or learner access. An uncertain upload stops before save. An uncertain save stays unconfirmed. Neither step repeats automatically. [Native upload](https://github.com/moodle/moodle/blob/v5.2.2/public/repository/upload/lib.php), [file-picker request](https://github.com/moodle/moodle/blob/v5.2.2/public/repository/filepicker.js), [saved Resource preparation](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/resource/mod_form.php), [IMS package form](https://github.com/moodle/moodle/blob/v5.2.2/public/mod/imscp/mod_form.php).

The existing bridge message limit is 2 MiB. A raw-file limit of 1 MiB leaves room for base64 and the command envelope; native limits can be lower. This is a transport limit, not full file coverage. The current effect journal stores forwarded arguments. File bytes therefore need bounded process memory and an opaque handle before planning. Plans and reviews contain immutable metadata, not base64. Dispatch resolves only the approved handle and rechecks its bytes. Missing bytes after a restart must refuse before send. The existing `ArtifactGenerationRegistry` stores digests only; it does not retain upload bytes. The browser side now also replaces the file of a Resource, deletes one extra Resource file, adds up to 8 reviewed files of at most 1 MiB together to one Folder path in the given order, and creates one empty subfolder under an existing path, which reaches any depth one approved subfolder at a time. That 1 MiB total for a set is the same raw-file limit: one bridge message carries every reviewed file of one approval. Those four have browser-fixture proof only, and the local file planner stages one file for one new activity, so it does not yet stage a replacement file or several files at once. Larger files, a set above 1 MiB together, replacing or deleting a Folder file, aliases, and editor attachments remain required later work.

## Browser transport limit

Morrow starts one explicit native request per approved dispatch. Chrome can resend that request after a connection error; this is not a general exactly-once provider-effect contract. The [isolated transport evidence](BROWSER-POST-TRANSPORT-LIMIT.md) records the duplicate POST and the required unconfirmed state. Normal-path POST counts prove only their recorded run.

## Test and proof requirements

For each new operation:

1. Add one compact local success test and one critical refusal or mismatch test when existing tests cannot cover the changed contract.
2. Test exact binding: origin, subpath, principal, course or system context, and module/object identity.
3. Test native form/action uniqueness, protected-field preservation, CSRF confinement, bounded response handling, and secret/draft stripping.
4. For writes, test reviewed inputs, pre-send stale-state refusal, one dispatch, authoritative saved-state readback, and replay refusal. Treat redirect, HTTP success, or a provider message as insufficient.
5. Run the focused tests, then the repository source gate after a coherent feature layer is complete.
6. Run a separate signed-in Moodle proof on an authorized disposable target for each write class. Record the exact target, request review, dispatch count, authoritative result, replay refusal, role/capability context, and limitation. A public-demo reset makes a receipt historical evidence, not ongoing tenant proof. `scripts/moodle-live-proof.mjs` runs that proof and writes that receipt: `--target=site --site=<https origin> --chrome-profile=<directory> --course-id=<id>` against the authorized target, `--target=fixture` against the local HTTPS fixture it serves. [MOODLE-LIVE-PROOF-CHECKLIST.md](MOODLE-LIVE-PROOF-CHECKLIST.md) lists every catalog write with its required proof fields and its current evidence state.
7. Test at least the standard editing-teacher path. Add a role-specific proof before claiming support for a different capability combination. Test a custom course format or refuse it until its effects are defined.
8. For files, grades, people, reports, backups, restores, and administration, prove data minimization and target scope before enabling broad reads or writes.

## Completion criteria

Moodle full functionality is complete only when all conditions below are true:

- Every one of the 23 core modules and every one of the 17 authorable core question types has a documented, implemented, tested, and live-proven capability matrix for its applicable author, learner, grading, file, completion, reporting, lifecycle, and deletion workflows.
- All cross-cutting rows in this document, including system administration, have equivalent contract and proof. Role and site authorization remain explicit in the product interface.
- Every enabled core operation binds the signed-in account and exact native target, preserves protected state, confines secrets, reads back the saved result, and refuses a replay or uncertain resend.
- Moodle supports analysis and reviewed changes across dozens of selected courses through the shared batch workflow. Each course remains separately identified through review, scheduling, progress, failure, restart, cancellation, and saved-result verification. This is a shared Canvas, Moodle, and Blackboard requirement.
- Users install only the Morrow MCP package and Chrome bridge. Required local services and runtime support must fit inside those items and start through the packaged setup path.
- Unsupported optional plugins are shown as unavailable until their installed-site inventory and proof are complete. Core completion never claims arbitrary third-party plugin coverage.
- The public and approval UI describe only the proven capability and role scope. Catalog totals and HTTP success do not count as parity proof.
- The dated evidence and remaining limits in [THREE-LMS-BRIDGE-PARITY.md](THREE-LMS-BRIDGE-PARITY.md) are updated when a row transitions from partial to complete.
