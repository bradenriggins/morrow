# Browser POST transport limit

Checked 6 September 2026. This is a confirmed limit of the signed-in browser transport.

Morrow reserves one dispatch and starts one explicit browser request. It does not automatically repeat a dispatched operation after an uncertain result. Those controls do **not** guarantee one network request or exactly one provider effect. Chrome can transparently resend a POST when a reused connection fails before response headers arrive.

The isolated [reproduction script](../../scripts/repro/moodle-gradebook-post-transport-retry-repro.mjs) uses a local HTTPS server. The server applies a synthetic rename, then drops the socket. The [receipt](../../output/research/moodle-gradebook-post-transport-retry-repro.json) records Chrome for Testing 151.0.7922.34, HTTP/1.1, one explicit `fetch`, two server-observed POSTs on two connections, and a rejected fetch. No Moodle account, course, learner, or live provider was used.

Independent checks reproduced the duplicate with `redirect: "follow"`, `"manual"`, and `"error"`. Redirect control does not disable network retries. A streamed body with `duplex: "half"` failed before send on HTTP/1.1. One HTTP/2 stream experiment observed one POST, but Chromium can buffer and rewind stream uploads. It is not an at-most-once guarantee. [Network transaction resend logic](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/http/http_network_transaction.cc), [POST resend tests](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/http/http_network_transaction_unittest.cc), [buffered chunked upload stream](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/base/chunked_upload_data_stream.cc).

The gradebook helper records the attempt immediately before its POST. A lost response or post-send exception returns `sent: true`, `outcomeUnknown: true`, and unconfirmed verification. The bridge converts that result to `write_outcome_unknown`. Morrow retains the operation and its conflict lock. A later new approval must not bypass that unresolved record.

A normal-path receipt that counted one server POST remains evidence for that run. A focused response-loss wrapper proves one explicit helper call and refusal to resend; it does not prove a browser-level delivery guarantee. Documentation must distinguish these facts.

General exactly-once provider effects would require a provider-enforced deduplication contract or an equivalent authoritative operation record. The current native Moodle form and AJAX routes do not provide that contract. An uncertain creation can therefore require checking for more than one created object. Morrow must keep unread or unresolved results explicit and must not manufacture a verification receipt to release them.

For an unresolved Canvas create, that check is implemented. The extension retains the parent-collection read with the operation record, and `morrow_operation_reconcile` counts the records that carry the requested field set and were created inside the request's window. More than one is reported as `duplicate_effect_suspected`; the record stays unresolved and locked, and the result names the manual step — open the course in Canvas and delete the copies the person does not want. Morrow deletes nothing. Records without a creation time cannot be separated from course work that was already there, so two matching records are reported as a suspected duplicate and one matching record proves nothing. This behaviour is proved against synthetic Canvas fixtures and stays live-unverified against a customer Canvas tenant. The Moodle routes still have no equivalent retained comparator.
