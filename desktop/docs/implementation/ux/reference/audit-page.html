Morrow · Bridge and desktop app · UI audit · version 5 · 21 Sep 2026

Design the four moments a teacher has with Morrow. The settings page is not one of them.

Third pass. Version 2 moved permission into the approval moment, and that holds. But it still ignored the largest daily cost: one approved change takes two app switches, a hunt for a link, a click, and a typed “done”, because Morrow never tells the assistant that the review is complete. The plan puts the moments in order of how often a teacher meets them and gives each one a measured budget. Every decision is now made. I made each one from Morrow’s own principles, and no part of the plan waits for an answer from you.

Third pass: what version 2 still got wrong

T1Missed

The review loop is the product, and it has no design

Morrow returns a loopback link in a tool result. The assistant writes its own sentence around it. The teacher finds the link, goes to Chrome, approves, comes back, and types that it is done. Only then does the assistant read the result. Morrow’s instructions to the assistant are 3,943 characters and say nothing about how to present the link or how to continue. No tool waits for the approval. The Bridge icon has no badge.

T10Missed

58 of the 347 grantable options grant nothing when selected

Found while I wrote the build spec. An option with more than 8 changeable settings gets an empty field list, so a grant of it lets Morrow change nothing. What the research says

Ask at the moment of need

Apple: request access only when the feature needs it, explain why in one active sentence, and give defaults so people can start at once. HIG Privacy, Onboarding

Keep people in control of AI work

Apple: put Undo and Retry near the result, do not automate actions that are hard to reverse, confirm significant actions, show specific progress, and give example requests. HIG Generative AI

Confirm only what is serious

Routine confirmations train people to click without reading. Name the exact object and action. Prefer recovery to confirmation. Nielsen Norman Group

Ask one time for each context

A field study of 36 Android users found that prompts work when they appear on first use in a context and only for sensitive data. A naive scheme would show 34 prompts on average. Wijesekera et al., USENIX Security 2015

The scope ladder is an industry pattern

VS Code’s agent asks with four scopes: one time, this session, this workspace, always. It also has one place to review and reset approvals, and it warns before a wide scope. Morrow’s ladder is: one time, this course for a fixed time. It has no “always”. VS Code approvals

Correction, consequences, global control

Microsoft’s guidelines for human and AI interaction: make correction efficient (G9), show what a choice will change later (G16), give global controls (G17), explain why (G11). HAX library

Who uses this

The teacher

Three to six courses in a term. Opens Morrow when there is a task: fix the quiz, move the dates, repair accessibility. Not technical. Will not read a settings page. Success is: ask, look at the preview, approve, done. The default experience must serve this person with no configuration.

The course designer or quality reviewer

Dozens of courses, many at one time, often the same change in each. Needs search by course code, filters, bulk level changes and a record of what changed. The list must scale for this person without a cost to the teacher.

The four moments

1. Start

Setup ends with a real result, not only “connected”. Three example requests with a Copy button. The first one finds something useful, for example images with no alternative text.

2. Ask and review

The assistant says one sentence and gives one link, named after the change. The teacher approves. The assistant continues with no typed message. The Bridge popup lists each review that waits.

3. Trust

The review offers “do not ask again for this kind of edit in this course”, for 4 hours, with a clock time. One switch, “Routine edits”, allows edits to what exists: text, titles, order, file names, alternative text. Morrow always asks before it creates, publishes, removes, posts, or changes a date, points or a setting.

4. Return and oversee

The Bridge opens the platform itself. The icon shows when Morrow can change a course. One click stops all access. “Recent changes” shows what Morrow did.

Moments 2 and 3: ask, review, trust

Play it. Open the review from the named link. Approve one time, and the next review is a batch. Select “do not ask again”, and the assistant completes the other images with no review. Then it asks to delete a page, and that review is different.

Your courses

Safety. A wide grant lets text hidden in course content steer more changes with no review. Morrow tells the assistant to treat course content as data, but that is an instruction, not a barrier. A grant that comes from one approval is the narrowest grant possible, so the simple path is also the safe path. The review page needs a one-time code and a cookie, so the assistant cannot approve for the teacher.

Customize view: Edit access with progressive disclosure

This is the advanced view. A person reaches it from “Customize” on a course. Most teachers never open it. It has three levels. Level 1 is 8 areas of teacher work. Level 2 is the kind of change: create and edit, publish and organize, remove. Level 3 is the single action. Each level has “select all”. A preset fills the list in one click. The bar at the bottom says the grant in plain words.

Plan

Implementation detail is in the Morrow UX Build Spec: every decision made, a Foundation phase with exact tokens, 47 work items with files, functions, data shapes, text, tests and acceptance checks, and 19 validated Canvas bundles.

Six phases, in order of how often a teacher meets the problem. Each phase ships alone. A baseline walkthrough comes first, so each later phase has a number to beat.

Baseline walkthrough Small · before any change

Measure today’s build, so “better” is a number. No person must be recruited.

Method

  • The implementer does seven tasks on a clean user account with a sandbox course: set up to first read; correct alternative text on one page; move three due dates; come back with tabs closed; find what Morrow changed; set access for 12 courses by code; stop all access.
  • Record for each task: clicks, app switches, typed messages, seconds, and each place where the text on screen was not sufficient.

Done when

  • Each row of the interaction budget has a measured baseline.
  • Sessions with teachers come after phase 4. They correct labels. They never block a release.

The gate that no UI work can repair

Chrome Web Store listing. Until it exists, a new person must turn on Developer mode and use “Load unpacked”, five manual steps. Plan the listing as its own track.

Release constraints

Sealed Bridge releases. Each Bridge source change needs a manifest version bump, a new sealed entry in connector/release-ledger.json and a run of scripts/package-canvas-connector.mjs. Batch each phase into one release.

Pinned tests. The gate pins option counts, document line citations and a no-em-dash rule. Phases 3 and 5 will move some pins. Update them on purpose, in the same commit.

Shared worktree. A second lane commits to this worktree now. Do the UI work in its own worktree and branch.

Decisions, made

You asked for no decisions. I made each one from what Morrow says about itself: “Show the next useful action before technical details.” “Keep permission, changes, consequences, and uncertainty visible.” People “should not need to understand browser connections or server internals.” “You keep the teaching decisions.” “Morrow does not add another chat interface.” “Calm, clear, capable.” Sources: docs/brand/MORROW-BRAND.md, .better-web-ui.md, README.md. The build spec has the full table with the reason for each.

The Bridge opens Canvas or Moodle by itself when work needs a closed site.

Yes, by default, with no consent step. A tab is mechanics. It gives Morrow no new data and no new permission. One setting turns it off, and the popup says what happened.

The Bridge opens the review page by itself.

No. A tab that takes focus is not calm. The assistant gives one link, named after the change, and the popup lists each review that waits.

A one-switch level.

Yes. Its name is “Routine edits”. It changes what exists: text, titles, order, file names, alternative text. It never creates, publishes, removes or posts, and it changes no date, points or setting. The included bundles are always listed under the switch.

Dates with no review.

Only from “do not ask again” on a date review. Never from the switch. A date change sends a notice to learners, and a batch of dates costs one click to review.

How long “do not ask again” lasts.

4 hours, shown as a clock time. One work session. A new kind never moves the end time later.

Approval in the assistant’s native form.

No. Not built. Morrow’s promise is that you review the exact change in Morrow. One place to approve.

Web pages from the desktop app.

Exactly two fixed addresses. The store listing opens in Chrome. The support page opens in the default browser.

“Select all” and removal.

Never together. Removal is a separate checkbox, in the Customize view only, with the present confirm step.

The names Plan and Edit.

Kept, and always with the meaning: “Plan. Morrow asks first.” and “Edit. Selected edits run without another approval.”

A tray or menu bar item.

No. The plan removes surfaces. The Bridge icon shows state where the work is.

Tests with real people before a release.

Not required. A walkthrough with counts proves the budget. Sessions with teachers after phase 4 correct labels and never block.

Would Apple ship it?

The model: yes. The product: not until two things are true. The Chrome Web Store listing must exist, and the interaction budget must hold in the walkthrough with counts. A plan is a claim. The counts are the proof.
