# Limitations

Morrow `1.0.2` is the current release build. Publication and live verification remain subject to the evidence below. The version is not an Instructure authorization claim.

## Platform coverage

This is the canonical platform sentence. Every Morrow surface that states platform coverage, including the website, the desktop app, the extension, and the README, quotes it exactly as written here:

> Morrow works with Canvas and Moodle through the signed-in Chrome connection and with Blackboard through the official Anthology Learn REST API; Canvas has selected live test-course proof, part of the Moodle catalog has been checked on a signed-in Moodle test course, and no live Blackboard tenant has been tested.

Morrow is working toward the same core features across all three platforms. It does not claim current parity. The checked and unchecked Moodle operation counts are in the Moodle product limits below, and the Blackboard route, review contract, and evidence are in the Blackboard product limits below. A surface with room for one platform only quotes that platform's clause from the sentence, with its words unchanged. A surface that needs more detail than the sentence carries states it from those limits; it does not restate the sentence in other words.

## Current external gates

- The automated browser campaign uses a synthetic Canvas estate. Separate authorized [BT2 tests](docs/implementation/BT2-LIVE-PROOF.md) record selected live lesson, quiz, module, learner, page-create, and native Codex update results. They do not prove the full Canvas catalog or live Item Bank compatibility.
- Client configuration parity is tested for ChatGPT/Codex, Claude Code, Claude desktop chat, and Gemini CLI. Each available real client still needs the complete live scenario before a cross-client production claim.
- A dated macOS Apple silicon archive passed a separate iMac recipient check with no global Node/pnpm, four bundled-SDK client health calls, one owner, and normal shutdown. The iMac Bridge was unpaired. Later source corrections still need a new archive and repeated proof; this does not establish full live-client or cross-platform support.
- The unsigned macOS Apple silicon 1.0.0 disk image was mounted, copied into an isolated installation, and launched on the MacBook on 7 September. It wrote a passing contained receipt under `scripts/test/desktop-mac-smoke.mjs`: the sealed payload verified, the gateway answered, the Bridge listener bound, and local state used modes `0700` and `0600`. The app retained the selected assistant and materials folder when replacing the earlier build. This does not prove a public-download Gatekeeper path or live-course pairing. Signing and notarization are outside this unsigned release.
- Public source-rights review and explicit publication authorization are separate release gates.
- Morrow Bridge has no Chrome Web Store listing. The desktop app keeps one app-owned unpacked Bridge folder and guides the temporary Chrome Developer-mode route: **Show Bridge folder**, then **Developer mode** and **Load unpacked** in Chrome. The app refuses to replace, reload, or grant permissions to a Chrome Web Store installation. From source, the extension installs unpacked from `connector/extension` or from a locally built deterministic archive.
- The Windows x64 1.0.0 installer is unsigned. On native Windows `BOOTZ`, `scripts/test/desktop-windows-smoke.mjs` passed install, startup, damaged-payload refusal, exact repair, uninstall, and byte-for-byte retention of the configured upstream, assistant settings and journal. The harness runs on native Windows only and uses isolated state. These checks do not prove SmartScreen behavior after a public download, institution-managed deployment, or live course access. The saved evidence is listed in the completion goal.
- Morrow builds for macOS on Apple silicon and for Windows on x64 only. `installer/electron-builder.config.cjs` declares `dmg` and `zip` for `arm64` and `nsis` for `x64`, and `scripts/package-mcp-bundle.mjs` declares the two matching payload targets. There is no Intel macOS build and no Linux build; neither is supported.
- Automatic updates stay disabled in unsigned releases. `scripts/test/desktop-update-harness.test.mjs` checks the maintained `electron-updater` library for admission, download, SHA-512 verification, cancellation, downgrade refusal and restart leases. It does not install an update. Unsigned builds use manual installer replacement; signing and signed automatic-update proof are outside this release. See [the update contract](installer/UPDATES.md).

## Product limits

- Canvas and Moodle use the signed-in Chrome connector. Canvas has selected live test-course proof. The Moodle catalog holds 250 operations, and only 31 of them have been checked on a signed-in Moodle test course: course and structure reads; Page, Assignment, and questionless Quiz creation; Page, Assignment-instruction, and Quiz-instruction edits; Assignment due dates and Quiz open/close dates; exact-slot question reads; Text and media area and URL Resource content edits; activity and section visibility; one activity move; Resource root-file metadata; and one reviewed Resource upload with saved-byte verification. That upload is limited to one workspace file of at most 1 MiB.
- The remaining 219 Moodle operations are implemented and pass local browser fixtures only. No signed-in Moodle site has run them. They cover Forums, Choices, Books and their chapters including chapter deletion, Lessons, Glossaries, Wikis, Feedback activities, Databases, Folders, IMS content packages, SCORM packages including a bounded settings edit and one package replacement for a hidden activity, SCORM attempt and learner tracking reads that a stock Moodle site refuses because it does not enable its SCORM web-service functions for the browser AJAX endpoint, the per-learner Assignment submission and feedback reads that a stock Moodle site refuses for the same reason, Text and media area and URL Resource creation, section and course-summary edits, whole-course show and hide, the gradebook configuration reads, the gradebook category and manual-item renames and the bounded gradebook category and manual-item configuration writes, the aggregate grader-report statistics and the roster-projected single-learner grade report, the course group map, Forum-post reads, aggregate Assignment submission, Quiz attempt and Forum activity summaries, the Quiz attempt record for one exact attempt and the aggregate Quiz manual grading queue and regrade state, which are read through Moodle's own Quiz report routes and never open the attempt, review or question-review page, the complete Assignment settings scope and the Assignment user and group overrides, the complete Quiz settings scope and the Quiz user and group overrides, the activity completion and course completion settings reads and writes, whose learner-visible result cannot be checked without a learner account and has not been checked, the course calendar reads and the course event create, change, and delete, whose wall-clock dates are read and written in the time zone the signed-in person has configured and never converted, the Question Bank filter inventory, the Question Bank impact scope for one course, and the dedicated hidden Question bank route: one hidden standard `mod_qbank` activity creation, a separately approved realization of that bank's default category, one new Multichoice, True/false, or Short answer question in that category, and a separately approved addition of that one entry to one approved Quiz. Treat every one of them as unproven on a real course. The complete list is in the [Moodle capability surface](README.md#moodle-capability-surface).
- Moodle Question-bank authoring is held because a bank change can affect random-question references outside the reviewed Quiz. The one exception is the dedicated hidden bank route: Morrow can create one new Multichoice, True/false, or Short answer question in a bank it created itself and add that one entry to one approved Quiz, each as its own approved change, and every later update to that question stays held. Morrow stops Moodle content and date changes when it finds attached files. Moodle file support replaces the file of a Resource, deletes one extra Resource file, adds up to 8 reviewed files of at most 1 MiB together to one Folder path, and creates one empty subfolder, each with browser-fixture proof only; it has no editor-attachment route. The assistant file planners stage Resource creation and replacement, multiple Folder files, SCORM creation and replacement, and H5P creation and replacement for review. See [provider scope](README.md#browser-connected-platforms).
- Blackboard works through the official Anthology Learn REST API with local credentials. A Blackboard administrator installs Morrow's REST application on the Learn site, chooses the Learn account the integration acts as, and grants that account the entitlements these routes need; no tenant has confirmed that entitlement list, so Morrow records every entitlement as unknown. The route inventory, the held operations, and the live-tenant acceptance runbook are in the [Blackboard REST scope](docs/implementation/BLACKBOARD-REST-SCOPE.md). Morrow does not sign in to Blackboard through the browser, and the Chrome connector does not connect a Blackboard course page. Morrow binds every Blackboard request to one configured HTTPS tenant origin, one integration account, and one course, and it refuses a course binding that does not derive from that exact tenant principal and course. The public Full MCP exposes the Blackboard reads and 15 reviewed action planners. The [README capability surface](README.md#blackboard-capability-surface) names them. In the tool surface the desktop app configures, no catalog tool is registered under its own name, and an assistant reaches each Blackboard read by that same name through `morrow_capability_read`; the planners are separate tools in both surfaces. The change operation reads the integration account, that account's course membership, the learner roster, the course, and the content item, then freezes the exact patch for review. It sends no Blackboard PATCH request. The apply and verification routes are private source tools: an MCP client cannot discover or call them, and the Blackboard server registers them only for the Gateway process that launched it, under a dispatch secret the Gateway creates for that one process. Before any provider read, the apply route checks the signed one-use effect grant and the exact reviewed plan digest. It then re-reads the item and refuses when any frozen protected field changed after review. Local mocked-HTTPS tests show that a forged grant, a cancelled operation, an unapproved operation, and a replayed grant each send no PATCH, and that the approved path sends one PATCH and then reads the item again for a fresh saved-result comparison. Morrow keeps its own record of the Blackboard changes it has already sent, as one private file in its state folder, so a replayed grant is refused after Morrow restarts and not only inside the run that spent the receipt. When a change request leaves Morrow and Blackboard does not confirm what it did with it, Morrow refuses a new change to that exact item, through a restart, until somebody asks Morrow to check that saved request; `blackboard_unresolved_effects` lists the changes waiting for that check, and Morrow never sends such a change again on its own. While that record cannot be read or written, Morrow keeps reading Blackboard and refuses every change. A real interruption in the middle of a Blackboard PATCH has not been tested: the local tests drive the same recorded phases through a failing request. Learner identities are redacted before any Blackboard result leaves the server. When Morrow cannot read the whole course roster, cannot resolve one course membership to a person, or cannot remove every learner identity from a field, it refuses the whole result and names that condition instead of returning the rest of it. A field marked as withheld in a returned result means only that Blackboard did not return that field as text. Every Blackboard read checks the integration account and that account's course membership again. It reuses the learner roster it read for that course for at most 60 seconds, so a read inside that minute does not recognize a person enrolled since that roster read. A roster summary, a change plan, and the saved-result check after a change read the roster again.
- Blackboard supports reviewed content metadata and dated visibility, course availability, an existing membership role or availability, gradebook column settings and a person’s score or grade text, one workspace file attachment, a new Ultra assignment, announcement creation and editing, group creation and editing, group membership addition and removal, and an exact course copy into a new course ID. File attachments use one workspace file of at most 1 MiB. Blackboard can notify enrolled learners when an announcement is posted; Morrow cannot recall those notifications. Creating an Ultra assignment also creates its gradebook column, and Morrow has no undo route for either. A course copy is asynchronous and cannot be undone here; Morrow retains Blackboard's task reference and verifies the copied course only after the task reports completion. Content metadata changes are limited to a `resource/x-bb-document` item’s title, description and availability. Document bodies, tests, questions, question banks, discussions, forums, course enrolment creation or removal, standalone gradebook column creation or deletion, and group or group-set deletion remain unavailable. These limits follow the current implementation and the documented REST contract; no live tenant has been tested. Protected learner references can be used by an assistant for one exact course. The identity map is encrypted in private local state and survives a restart. All Blackboard evidence remains local mocked-HTTPS proof only.

- MindTap and Connect are not supported, listed, or callable. See the [inclusion review](docs/release/CONNECT-MINDTAP-INCLUSION-REVIEW-2026-09-05.md) for evidence reviewed and open decisions.
- The three Canvas course aggregate reads, `canvas_get_assignment_submission_summary`, `canvas_get_course_gradebook_summary` and `canvas_get_course_activity_summary`, count learner work inside the Canvas page and return counts only. No signed-in Canvas course has run them, so the aggregation contract is live-unverified: real submission and gradebook payloads vary by tenant and role, and a role without grading rights sees no needs-grading count, which the summary reports as unavailable rather than inferring one. The gradebook summary suppresses a score distribution below 5 scored submissions and whenever a band would hold 1 to 4 of them; that threshold is proved against fixture cohorts only, not against a real class. The activity summary compares each row's `updated_at`, and a Canvas resource whose rows do not carry that field is reported as unavailable for that kind rather than counted as unchanged.
- A Canvas audit's `render_evidence` is a saved-source render signal, live-unverified. Morrow Bridge parses the same saved field again in an isolated extension page whose content security policy is `default-src 'none'`, so that page loads no image, media, style, font or script and reaches no network. A detached document there is not the learner's Canvas page: it has no course theme CSS, no Canvas chrome, no real focus behaviour and no assistive-technology output. It reports focus order against DOM order for a positive `tabindex` only, the accessible name of every link and button, links that read alike but lead elsewhere, table header association, MathML and equation images, `track` kinds and declared controls per media element, and a WCAG contrast ratio only where the foreground colour is in an inline `style` on the element and the background colour is in an inline `style` on that element or an explicit ancestor. Every other colour pair, the rendered text size, focus visibility, real tab order, player controls, equation rendering, table reading order and assistive-technology output are returned as `not_determinable_without_course_theme`. It is never a rendered learner-view check and never a conformance result, and a read with no record returns `status: "not_observed"` rather than a pass.
- The connector can act only with the permissions of the current signed-in Canvas or Moodle user.
- The connector needs an open, signed-in Canvas or Moodle tab. Canvas Item Bank operations also need an authenticated New Quizzes frame for the selected tenant and course.
- Morrow reads and changes Canvas Item Banks. The Canvas catalog contains seven Item Bank reads and eleven course-bound changes: create, rename and delete a bank; create, update, attach and remove a question; share a bank with one course as read access; and add or remove a bank draw or bank entry on one New Quiz. Every change reads the exact current state first, requires the digests the reviewer approved, sends one request, and rereads Canvas to prove the saved result. Local fixtures prove these boundaries. No Morrow-connected Canvas tenant has answered the private bank or builder routes, so the contract remains live-unverified. The attended checks are in [ITEM-BANK-LIVE-PROOF-PLAN.md](docs/implementation/ITEM-BANK-LIVE-PROOF-PLAN.md).
- When Morrow changes a New Quizzes question that Canvas already holds, it compares the change against the question it just read and refuses only a media problem the change would add. So it will add alternative text to one image in a question whose other images still have none, and it will still refuse a change that brings in a new undescribed image, a second copy of an existing one, or a media address Canvas cannot serve. Two consequences follow, and both stop the change rather than send it. Changing another attribute of an image that has no alternative text, its width for example, is refused until that image is also given alternative text: add the alternative text in the same change. A question whose saved body contains media markup Morrow cannot read to its end cannot be changed through Morrow at all: open that question in Canvas, fix the markup there, and Morrow can work with it again.
- Canvas exposes no authoritative account-wide reverse lookup from an Item Bank to every New Quiz that uses it. `morrow_read_item_bank_fan_out` therefore reports observed uses only and always stays incomplete. Changing an existing bank requires that record and the reviewer's acknowledgement of the exact courses it names outside the selected one. A record that claims complete reach, or that hides an observed course, is refused before Canvas receives the change. Acknowledging the observed courses is not proof that no other course uses the bank.
- For every Item Bank operation, Morrow opens an inactive temporary tab at the selected numeric course's exact `/external_tools/54065` launch. Canvas's own Item Banks client supplies the private context UUID and `Authorization` plus `AuthType: Signature` request headers on its first same-frame bank-list request. The service worker captures them only after exact tab, frame, same-tenant API origin, launch nonce, numeric course, and time checks. It keeps them in memory. It never writes them to extension storage, the bridge protocol, MCP output, logs, or client configuration. The executor uses the private context UUID for the provider's bank-list `course_id` value and keeps the selected numeric Canvas course as a separate `canvasLocalContextId`. It closes the temporary tab and clears the credential after the operation.
- `canvas_item_bank_list_shares` makes one unpaged request and always reports `paginationUnestablished`. No attended provider proof establishes share-list page parameters or an end signal, so a bank's share snapshot and the share readback cover exactly what Canvas returned in that one response. Morrow shares a bank with a course as read access only. Sharing with a user, an account or a subaccount, granting edit access, and changing or removing an existing share are all absent.
- A New Quiz settings change sends the complete settings block, never part of one, because a partial block can replace the settings nobody asked to change and take a published quiz's learner result view with it. `morrow_plan_new_quiz_settings` reads the complete saved block, validates setting names, types, enums, date and IP formats, and parent-child dependencies, merges the requested changes, and supplies the exact current-settings digest. The connector reads the quiz immediately before the change, refuses stale or unreadable settings, sends the complete merged block, and reads the complete block again. It reports every key the plan carried over. Whether the New Quizzes service accepts the JSON request and every documented setting combination is live-unverified.
- A New Quiz question is never changed in place in a way that renumbers its parts. Before any in-place content or position change, the connector reads that question from Canvas and requires exact `mutable` status, no provider lock, and no stimulus relationship. It refuses the change when the requested answer data would add, remove, rename, or duplicate any provider interaction UUID or leave a scoring reference invalid, and it refuses the change outright when it cannot read the question first. Morrow has not verified the provider's handling of newly generated interaction UUIDs on a live tenant. Structural changes use separate reviewed delete and create operations. Morrow plans that pair and never sends it: `morrow_plan_new_quiz_item_replacement` reads the current question, keeps every author-controlled field the request leaves out, omits documented provider-assigned response fields from the saved item, and refuses a caller-supplied provider field, an unrecognized saved field, a provider status other than exact `mutable`, a provider lock, or a stimulus relationship. Otherwise it returns a delete and an add in that order. The pair is not atomic. If the delete succeeds and the add then fails, the quiz holds one fewer question until somebody adds it again, and the saved question list is the authority on what the quiz holds. `morrow_plan_new_quiz_item_create` and `morrow_plan_new_quiz_item_delete` plan the same two routes one at a time; a delete of a question the quiz no longer holds plans nothing. Create and delete dispatch require the planner's digest of the complete fresh membership, including every row's ID, position, and entry type. A quiz may contain Stimulus or bank-backed rows, but they cannot be the direct lifecycle target. A delete also freezes the complete target item digest. The Bridge refuses stale membership, a changed target, a target that is not an Item, a stimulus link, a provider status other than exact `mutable`, a provider lock, a changed create payload, or an invalid positive-integer position before the write. It reads the complete membership after delete, and it reads the complete membership plus the created item after create. A lost response triggers those reads and never a second write. None of these three has run against a live Canvas course. The general New Quiz question update stays offered for review only and cannot be granted Edit access; the focused New Quiz image alternative-text repairs, for the question, one answer choice, answer feedback, and question feedback, keep every id and stay available. A saved Edit grant that named the general New Quiz question update no longer validates, and the person is asked to grant access again.
- A Classic Quiz question image alternative-text repair rebuilds the whole question, and no live Canvas tenant has proved that round trip. Canvas rebuilds a Classic Quiz question from the whole request through `AssessmentQuestion.parse_question`, so a field the request leaves out is rebuilt from a default rather than kept. `morrow_plan_classic_quiz_question_image_alt_repair` therefore reads the question again in the connected tab, resends every field that read returned, and changes one escaped `alt` attribute in the question text or in one answer field. It refuses a question that carries a `quiz_group_id`, because Canvas can rebuild that question from a question bank; a question type outside `multiple_choice_question`, `true_false_question`, `multiple_answers_question`, `short_answer_question` and `essay_question`; a read that omits a field the write must resend; and a read that carries any question or answer field this write cannot send back. After the write it reads the question again and compares the whole saved question except the one edited field, so a rebuild that changed anything else is reported as a mismatch rather than a success. Hidden question state that Canvas never returns to a read cannot be compared at all, so this repair keeps its own Edit category and stays live-unverified.
- Every complete New Quizzes question payload the governed lifecycle would plan for create or replacement is read against the documented shape for its interaction type first. A question that fails the check is refused before a plan exists. The local contract covers Multiple Answer, Matching, Categorization, File Upload, Formula, Ordering, Rich Fill in the Blank, Hot Spot, Multiple Choice, Numeric, True or False, and Essay. It validates the applicable provider UUIDs, scoring references and algorithms, interaction properties, feedback maps, formula variables, precision values, and answer shapes. Hot Spot creation plans with the reviewed media-byte upload and confirmation chain: the reviewed bytes go once to the presigned host Canvas named, and the create is refused unless the upload observer confirmed that exact request. It also refuses deprecated Fill in the Blank and any stimulus, text-block, bank-item, bank-entry, or bank-draw create shape. Two accessibility rules run for every supported question type: an `<img>` with no `alt` attribute is refused, and so is an image, audio, or video source that is not an `https://` address, a `/courses/` path, or an `/api/v1/files/` path. An `alt=""` marks a decorative image and passes, because that is the author's answer rather than a missing one. The complete check runs in `morrow_plan_new_quiz_item_create` and `morrow_plan_new_quiz_item_replacement` before either plan exists. Item Bank question updates use a separate complete-item snapshot and readback contract. A definition change does not regrade completed submissions. Regrading is a separate SpeedGrader action. Canvas documents no regrade for Essay or File Upload questions, and Categorization regrading can change points but not correct answers. Whether Canvas accepts a payload these rules pass is live-unverified.
- A Canvas course section can be renamed, redated, or removed only after Morrow reads that section in the connected tab and Canvas names the selected course as its owner. Morrow reads the section again after the change, and a removal also has to be gone from the selected course's complete section list. Every section route that carries a student's submissions, grades, enrollments, or assignment overrides stays held under its own reason, and cross-listing a section between two courses stays held. The section fields used here come from the published Canvas specification; no live tenant has run these two routes, so section changes are live-unverified.
- A Canvas group's own discussion topics and pages can be changed only after Morrow reads that group in the connected tab, Canvas names a course as the group's owner, that course is the selected one, and the selected course's own complete list of groups names the group. A group Canvas records under a person or an account, a group in another course, and a group the selected course does not list are all refused before anything is sent. Morrow reads the changed topic or page again through its own Canvas route. Every route that places, moves, or removes people stays held under the learner reason, and every change to a group object, a group set, or a group's files stays held: changing a group set can create groups and place students in them. The group fields used here come from the published Canvas specification; no live tenant has run these routes, so group changes are live-unverified, and group visibility and privacy on a real tenant, including any difference between a teacher and a teaching assistant, is untested.
- A Canvas course file can be renamed, moved to another folder in the same course, or removed, and a folder can be added inside a course folder, only after Morrow reads that file or folder in the connected tab, Canvas names a course as its owner, that course is the selected one, and the selected course's own complete list of files or folders names the object. A move is sent only when the destination folder is in that same list, and a rename or a move is sent only with the instruction that keeps a file which already has the new name, because Canvas otherwise replaces it. Morrow freezes the file's saved version, including its id, saved-at time, size, and type, reads the file or folder again through its own Canvas route afterwards, and reports a mismatch when the reading is not that same saved object. A removal is proved by a route that no longer answers or by the course's own list no longer naming the file. Copying a file or a folder stays held, because the copy lands in a second object this reading does not prove, and so do the folder object itself, the folder upload route, and every account, group, and user file route. A Canvas file link carries a signed verifier, so the result of one of these file changes carries the saved record without its links. The file and folder fields used here come from the published Canvas specification; no live tenant has run these routes, so course file and folder changes are live-unverified, and a tenant whose file reading does not name its owning course refuses the change instead of sending it. Canvas usage rights are not part of these routes and are untested.
- A Canvas calendar event can be added to the selected course's calendar, changed, or removed, and an appointment group can be changed, only when Canvas names that course's calendar on the object. A new event carries the selected course's context code in the request itself and is read back from its own Canvas route afterwards, where Canvas has to name that same calendar. An existing event or appointment group is read in the connected tab first, and a change that would move an event to another calendar is refused. Morrow compares the title, start time, end time, description, and location it asked for against the event Canvas saved. A removal is proved by a route that no longer answers, or by the selected course's whole calendar, asked for by that calendar's context code and read to its last page, no longer naming the event; a listing that came back holding another calendar's events is treated as unreadable rather than as absence. An appointment group that serves more than one course at once is refused outright, whether the request names the second course or the saved group does, because the same change would land in the other course too. Morrow sends one event and reads that one event back, so a repeat rule, a duplicate count, a series choice, and section-level start and end times are refused before anything is sent, and so are the sub contexts that narrow an appointment group to particular sections or to a group set. Reserving a time slot, and deleting an appointment group, which cancels every slot already booked in it, stay held under the learner reason; creating an appointment group stays held, because the request names its courses itself and nothing proves those are the selected one. The calendar fields used here come from the published Canvas specification; no live tenant has run these routes, so course calendar changes are live-unverified. The context-code formats for section-level and multi-course events are untested here, and so is Canvas's own handling of the whole-calendar listing the removal proof depends on.
- The connector does not reuse authentication from ChatGPT, Claude, or another application's in-app browser.
- A person must reload the unpacked Morrow Bridge in Chrome. The desktop app verifies the bundled Bridge release manifest, keeps a rollback copy, swaps the folder atomically, and then waits: it does not open or automate Chrome's extension page. Until the reloaded Bridge returns the exact new version and the active-folder proof, the app reports the update unconfirmed. A complete update through a normal signed-in Chrome profile is live-unverified; the active-folder challenge is proved on an isolated Chrome-for-Testing profile only.
- Canvas File text reads, PDF and Office structural signal reads, and reviewed file transfers require a separate local opt-in and Chrome HTTPS file-access permission. A reviewed transfer also uses the extension's static passive `webRequest` permission for one exact Canvas-issued upload response: both listeners are registered with that exact upload URL as their Chrome match pattern, so Chrome offers them no other request in the browser, and the transfer then confirms the result in the selected Canvas page. The browser fixture covers that observer, holds one upload open while a POST goes to another HTTPS host and proves the observer is offered no event for it, and covers the authenticated confirmation, but it is not a customer Canvas proof. Native grant, denial, and removal have isolated synthetic-host proof for file reads only. A PDF or Office file at most 1 MiB returns structural signals only (version, page, part, drawing description, heading style, slide and sheet counts, and presence states that say present, absent, or not determinable) and never its document text, so a signal set is never a pass and never an accessibility result. Those readers are proved against hand-built documents and a synthetic storage host only. A customer Canvas file host, document content, other binary files, and learner rendering remain unverified or manual.
- `morrow_program_ledger` states one final state for every target a selected-program inventory discovered, derived only from saved local audit and operation records. It reads no course, so every state is live-unverified. Its conformance claim is fixed to `none`: the saved-source signals do not establish WCAG conformance, and unread, blocked, held, and pending-review targets are not passed targets. A recorded manual check is the person's own statement, not Morrow evidence.
- Chrome grants optional site access per platform origin. A school that blocks extensions, frame execution, local WebSockets, or the platform connection can prevent operation.
- Content Security Policy or a future Canvas UI change can require a connector update. Catalog and browser tests detect known contract drift, but they cannot prevent provider changes.
- Only exact explicit course sets can create write batches. Morrow does not treat partial discovery as an all-courses target.
- A write without a safe frozen readback route is refused or remains unconfirmed. It is never reported as verified. Plan and Edit settings marks every Edit action in that state as `Saved result not checked` with the reason it cannot be checked, marks every action that removes content, offers a filter that lists only the actions Morrow can check, and asks for a second confirmation before it saves a selection that contains either kind.
- Undo is a new correction operation. Morrow does not pretend that every Canvas action has a lossless inverse.
- Checked page-text changes require bridge 1.0.4 or later and the matching local MCP. They replace one unique phrase in a complete, unfiltered rich-text page. They do not support block-editor pages, phrases split across HTML tags, or automatic undo. A fresh page and revision check detects stale reviews, but Canvas supplies no documented atomic edit lock for this request. Concurrent edits can still make the result unconfirmed.
- A provider timeout or lost response after send can become `applied_or_unknown`. Morrow does not replay it. A Canvas write the provider refused with a 4xx other than 408 or 429 saved nothing, so that record is `failed` and its course item stays free for another attempt; a 5xx, a 408, a 429, and any lost response stay uncertain, and that uncertain half is live-unverified. Connector operations use an immediate native saved-result check. A Canvas change that had a safe generic read route keeps that read-only comparator with its operation record, so a later check re-runs only the read and can settle the record to verified; the change is never sent again. Morrow refuses that check when the connected course, sign-in, or session is not the one the change was sent from. An unresolved record with no retained comparator (a record from an older version, a change with no safe read route, or a read Canvas would answer only with 404) stays unresolved and reports `reconciliation_requires_provider_evidence` with the item to open in Canvas. That record is not stuck: a person who reads the item with Morrow can close it with `morrow_operation_close_unresolved`, which requires the exact result digest of that fresh read and an explicit person confirmation. It moves the record to `closed_by_person`, releases the course item, sends nothing, and never reports the change as verified; every surface says that a person checked it and Morrow did not. A previously verified record keeps its verified result. Recovery is proved against synthetic Canvas fixtures only; it is live-unverified against a customer Canvas tenant.
- The record that stops one reviewed change from being sent twice is held in memory and is bounded: 20,000 changes in one Morrow Bridge run, and the most recent 2,000 in Chrome. Neither one forgets a change and then accepts it again. Morrow refuses a new change once its record is full and asks for a restart, and Chrome refuses a change prepared before the start of the record it still holds. The durable record on this computer stays the authority across a restart: it reserves one dispatch for an approved change and refuses a second.
- One Morrow dispatch is not a guarantee of one network request. A local Chrome test observed two POSTs after one explicit request when the server dropped the connection. Native browser retries can create duplicate effects even though Morrow does not retry the operation. When a Canvas create stays unresolved, the later check reads the parent collection and reports `duplicate_effect_suspected` if more than one record matches the requested fields inside the request's time window; it never deletes anything. That check needs a creation time on the collection records, and it reports a suspected duplicate rather than a confirmed one whenever the records carry none. See the [transport evidence and limits](docs/implementation/BROWSER-POST-TRANSPORT-LIMIT.md).
- Unresolved effects keep their provider-object conflict lock across clients and restarts. The refusal names the operation that holds the lock so the person knows which saved request to resolve. A potentially sent record from an older version may lack a provable target scope. Such a record blocks new connector dispatches across the installation. Morrow clears either lock only on its own verified readback or on a person-confirmed close-out that carries a fresh Morrow read digest; there is no automatic retry and no user-supplied verified toggle, and a close-out is never reported as verified.
- Large read results use bounded process-local handles. These handles do not survive a gateway restart.
- Durable operation and batch state is local to one Morrow installation. It is not a hosted synchronization service.
- Compatible client configurations can run at the same time when they use the same durable journal path and exact Morrow configuration. Their stdio proxies share one local-owner runtime. A configuration mismatch is rejected and cannot replace the running owner. Result handles remain local to one client session and are not shared. Every saved operation and request group records the assistant that asked for it: the client name and version that assistant reported at connect time, its stdio process id, its session, and the name and digest of its admitted project directory. The reported name is not verified and is not proof of identity, and the absolute project path is never returned to any assistant. `morrow_activity` answers what every connected assistant is doing now: the connected sessions, the groups that run and wait with the session that holds each batch window, every saved change that still holds a course item, the changes only a person can close, and the Bridge state with its connected sites. It reads saved state only and sends nothing to a learning platform. It reads the 200 most recent saved changes and request groups, and says when older records exist that it did not read.
- The desktop app changes the materials folder and removes an assistant after setup. Changing the folder writes the new folder into every assistant Morrow configured, and Claude Desktop then waits for its approval again, because that folder is inside the extension Morrow generates for it. Morrow rewrites an assistant configuration file only while that file still matches the file Morrow wrote, and it removes only its own entry: the `[mcp_servers.morrow]` table it appended to a Codex file, or the `morrow` key inside `mcpServers` in a JSON file. It removes that entry itself instead of through the `client-config` command that wrote it, so a change to what that command writes needs the same change in `installer/shared/installer-controller.cjs`. These changes are proved against real files in `installer/test/assistant-management.test.cjs`. No live ChatGPT, Claude Code, Claude desktop chat, or Gemini CLI installation has been observed reading a configuration file after one of these changes, so that side stays live-unverified.
- The desktop app's first read reads exactly one course, however many courses are connected. It counts every connected course, and it names the one Canvas or Moodle course it will read, before the read and after it completes, whenever the connection carries that course's name. It keeps that course while that course stays connected. A Blackboard course is connected through its own API and is never this browser read, so an installation whose connected courses are all Blackboard has no first read to run. Morrow refuses the result when the course binding changed between the moment it chose the course and the moment it dispatched the read. Two connected courses are proved in `installer/test/runtime-monitor.test.mjs` against a fixture runtime only. No two live signed-in courses have been connected at once, so the first read with more than one connected course is live-unverified.
- A running request group reports each course as it finishes, but only to a caller that asked for it. `morrow_batch_run` and `morrow_batch_resume` send one MCP progress notification for each child the run finishes: the children the group has settled, the children it froze, and one sentence naming the course and its outcome. That sentence is built from the frozen manifest and the settled child state, never from a provider result, so no learner identity reaches it. A caller that supplies no progress token sees the behaviour it saw before. Whether an assistant displays these notifications is that assistant's own behaviour, which Morrow neither controls nor proves.
- Morrow does not bypass Canvas role, course, account, New Quizzes, or Item Bank permissions.

## Security boundary

The browser connector prevents credentials from entering MCP messages, client configuration, logs, or durable operation records. It does not protect a computer that is already compromised, a malicious Chrome extension with broader access, or a malicious local process running as the same operating-system user.

The local approval page requires a separate decision outside the MCP tool surface. It checks the local origin, page nonce, and browser cookie. It cannot prove human presence against software with local HTTP or browser control. It is not multi-person institutional approval.

The desktop app's own half of that boundary is exercised as executed tests in `installer/test/adversarial.test.cjs` and `installer/test/adversarial-bridge.test.mjs`. They run the shipped code and check both halves of each answer: the refusal, and that the refused step changed nothing.

Each setup action refuses a request that is not the canonical setup page in the window's main frame. A setup request that carries an extra key is refused, and so is an argument to an action that takes none. A sealed payload file, a Bridge folder, a state folder, a rollback copy, or a Blackboard credential folder replaced by a symbolic link is refused. The data removal removes the path Morrow named and never the folder a link points at. An assistant settings file edited after Morrow wrote it is left exactly as it is. A record from a version this app cannot read asks for repair instead of being replaced. An interrupted Bridge update cannot be confirmed by a stale Chrome answer, by an answer from a Chrome Web Store installation, or once its rollback copy is gone. An update announced for another computer, another architecture, or an unreleased build downloads nothing. Work Morrow cannot confirm is idle keeps a verified update ready instead of restarting.

Windows access control cannot be read on macOS, so those cases are skipped with their reason and need a Windows host. These cases check the app's own file and message rules on this computer: no live Blackboard tenant has been tested.

## Release behavior

`pnpm package:connector` creates deterministic extension bytes and a SHA-256 receipt. `pnpm package:rc` creates deterministic private and public local candidate archives with a stage manifest, checksums, and CycloneDX SBOM.

Package creation does not publish software. A new stable release, a registry release, a Chrome Web Store release, or public provider claims require explicit release authorization and current receipts.
