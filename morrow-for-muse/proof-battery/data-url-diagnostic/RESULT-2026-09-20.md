## Verdict: data: URLs are NOT a viable brief transport.

Rendering and script execution in data: URLs work in the managed browser's
Chromium. But there is no shippable way to get the browser-task automation
to open one, and Chromium blocks the web-initiated workarounds.

## Evidence

### What works
- Part 1: `data:text/html,...marker-alpha-789...` rendered. Visible text
  "marker-alpha-789" confirmed via screenshot.
- Scripts execute inside data: URL pages (verified: a reduced test showed
  the script running and observing `document.body === null`, i.e. the
  script ran, the page was at fault, not the environment).
- Network from data: pages is fine: `https://httpbin.org/get` loaded in
  the same frame and returned JSON.

### What fails
- `goto` with a data: URL (even minimal `data:text/html,hello`) crashes
  the automation tool (`browser_process_failed`). The tool layer blocks it;
  no browser navigation error is observable because the tool dies first.
- Splitting as domain=`data:` + path gets rewritten to `https://data/...`
  (DNS error page).
- Omnibox unreachable (headless Chromium, no browser chrome; Ctrl+L lands
  in the page, F6 rejected by the tool).
- `https://httpbin.org/redirect-to?url=data:...` blocked by Chromium with
  `ERR_UNSAFE_REDIRECT`.
- Clicking a `data:` link with `target="_top"` from a subframe does NOT
  navigate the top frame. Chromium blocks web-initiated top-frame
  navigation to data: URLs. (Verified `target="_top"` works for an https
  link, so the block is data:-specific.)

### Part 2 (form POST) is INVALID, not negative
- The Part 2 page never submitted because of a page bug, not the
  environment: the inline script runs while the parser is still in `<head>`
  (document has only meta/title/script, no body), so `document.body` is
  null and `document.body.appendChild(f)` throws TypeError. The form is
  never created. No POST would occur in any browser with that page shape.
- The diagnostic loaded both data: URLs in a subframe via a clicked link
  hosted on the W3Schools tryit editor (neutral link host only). This path
  requires an externally hosted page and is not shippable.

## Classification

Managed-browser/platform launch blocker for the no-PAT lane transport.
There is currently no viable brief transport:
- loopback: unreachable from the managed-browser VM (separate leased VM)
- file://: crashes the managed browser (2026-09-20, twice)
- data:: automation cannot navigate to it; Chromium blocks workarounds
- hosted HTTPS: prohibited (product law)

The PAT lane (raw HTTPS) works, but PAT cannot be the only lane
(Braden's product law). The no-PAT lane has no transport until the
platform provides one.

## Directions for platform resolution (not built; no hosted workaround)

1. Platform fix: allow data: URL navigation in the browser-task automation,
   or provide a sanctioned way to open bundled page content.
2. JS execution: if the task supports running JS in page context, the
   brief could `document.write()` the bundled form host into about:blank
   (no navigation needed), or run `fetch()` in the Canvas page context
   with session cookies (this is also the PROVISION fetch-op direction).
3. Companion extension: ship a tiny extension with the connector that can
   open bundled pages. Bigger lift.

No hosted workaround will be built (product law).
